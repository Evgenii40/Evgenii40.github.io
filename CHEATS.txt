## Что такое MCP и зачем это нужно

**[MCP](/glossary/#mcp)** (Model Context Protocol) — открытый стандарт, который в ноябре 2024 года предложила Anthropic, чтобы ИИ-клиенты (Claude Desktop, Cursor, VS Code/Copilot, Cline, opencode и другие) единообразно подключались к внешним данным и действиям. Протокол построен на [JSON-RPC](/glossary/#json-rpc) 2.0.

Аналогия — «USB-C для ИИ»: вместо отдельного адаптера под каждую модель и каждую систему (1С, база, файлы, внешний сервис) вы один раз описываете **MCP-сервер**, и любой совместимый клиент может им пользоваться.

Сервер может отдавать клиенту три вида возможностей:

- **tools** — функции с типизированными аргументами, которые модель вызывает сама (у нас это `run_query` и `get_metadata`);
- **resources** — данные только для чтения, которые клиент подгружает в контекст (например, схема базы);
- **prompts** — готовые шаблоны запросов.

Общение идёт по одному из транспортов:

- **stdio** — клиент сам запускает сервер как локальный процесс и общается через stdin/stdout (используем этот вариант);
- **Streamable HTTP** — сервер работает по сети (в 2025 году заменил прежний HTTP+SSE).

## Что делаем мы

Сам MCP-сервер напишем на Python — о внутренностях 1С он не знает ничего. Все данные и действия выполняет опубликованный HTTP-сервис конфигурации:

```
ИИ-клиент  ⇄  MCP-сервер (Python, stdio)  ⇄  HTTP-сервис 1С  ⇄  база 1С
```

Почему так: 1С не умеет быть MCP-сервером напрямую, поэтому нужен мост. Конфигурация при этом трогается минимально — один сервис и один обработчик, а вся логика инструментов живёт в Python-коде.

## Что понадобится

- Python 3.10+ и менеджер пакетов `uv`;
- платформа 1С 8.3 с возможностью публикации (подойдёт и файловая база);
- веб-сервер для публикации — Apache 2.4 или IIS;
- любой MCP-клиент: Claude Desktop, Cursor, VS Code (Copilot), Cline, opencode и т. п.

## Варианты связи с 1С

| Вариант | Плюсы | Минусы |
|---|---|---|
| **HTTP-сервис 1С** (рекомендуется) | Кроссплатформенно, стандартная авторизация, работает и с файловой базой, и с серверной | Нужно опубликовать на веб-сервере (Apache/IIS) |
| [OData](/glossary/#odata) (стандартный интерфейс) | Включается одной галочкой, не нужен код в 1С | Даёт только CRUD по объектам, нельзя выполнять произвольные запросы и вызывать методы |
| COM-соединение (`V83.COMConnector`) | Не нужен веб-сервер | Только Windows, нестабильно, проблемы с версиями DLL |

Мы делаем гибрид: HTTP-сервис как «тонкий шлюз» (выполнить запрос, получить метаданные, вызвать метод) — он покрывает возможности и OData, и COM.

## Шаг 1 — HTTP-сервис в 1С

### Отдельный пользователь

В ИБ или Конфигураторе создайте пользователя `mcp_service` (обязательно имя латиницей — иначе Basic-аутентификация не сработает). Дайте ему минимально необходимые роли и **запретите интерактивный вход**. В идеале — создайте специальную роль `МСР_БазовыеПрава` только с правами на чтение нужных объектов.

### Создание сервиса

В Конфигураторе: **Общие → HTTP-сервисы → Добавить**.

- Имя: `MCPGateway`
- Корневой URL: `mcp`

Добавьте **шаблон URL**:

- Имя: `Execute`
- Шаблон: `/execute/*`
- Метод: **POST**, обработчик `ExecutePOST`.

Обработчик — тонкий универсальный шлюз, который принимает JSON с типом операции. Это позволяет добавлять новые инструменты в Python, почти не трогая 1С:

```bsl
Функция ExecutePOST(Запрос)

    Ответ = Новый HTTPСервисОтвет(200);

    Попытка
        Тело    = Запрос.ПолучитьТелоКакСтроку();
        Чтение  = Новый ЧтениеJSON;
        Чтение.УстановитьСтроку(Тело);
        ПараметрыЗапроса = ПрочитатьJSON(Чтение, Ложь);
        Чтение.Закрыть();

        Операция = ПараметрыЗапроса["operation"];

        Если Операция = "query" Тогда
            Результат = ВыполнитьЗапрос(ПараметрыЗапроса["query"],
                                        ПараметрыЗапроса.Получить("params"));
        ИначеЕсли Операция = "metadata" Тогда
            Результат = ОписаниеМетаданных(ПараметрыЗапроса.Получить("name"));
        Иначе
            Ответ.КодСостояния = 400;
            Результат = Новый Структура("error", "Неизвестная операция: " + Операция);
        КонецЕсли;

        Запись = Новый ЗаписьJSON;
        Запись.УстановитьСтроку(Новый НастройкиСериализацииJSON);
        ЗаписатьJSON(Запись, Результат);
        Ответ.УстановитьТелоИзСтроки(Запись.Закрыть());

    Исключение
        Ответ.КодСостояния = 500;
        Ответ.УстановитьТелоИзСтроки(
            "{\""error\"": \""" + СтрЗаменить(ОписаниеОшибки(), """", "'") + "\""}");
    КонецПопытки;

    Возврат Ответ;

КонецФункции
```

Вспомогательные функции (в том же модуле):

```bsl
Функция ВыполнитьЗапрос(ТекстЗапроса, ПараметрыЗапроса)

    Запрос = Новый Запрос(ТекстЗапроса);
    Если ПараметрыЗапроса <> Неопределено Тогда
        Для Каждого Пара Из ПараметрыЗапроса Цикл
            Запрос.УстановитьПараметр(Пара.Ключ, Пара.Значение);
        КонецЦикла;
    КонецЕсли;

    Выборка = Запрос.Выполнить().Выбрать();
    МассивСтрок = Новый Массив;
    Пока Выборка.Следующий() Цикл
        Строка = Новый Структура;
        Для Каждого Колонка Из Выборка.Колонки Цикл
            Строка.Вставить(Колонка.Имя, Выборка[Колонка.Имя]);
        КонецЦикла;
        МассивСтрок.Добавить(Строка);
    КонецЦикла;

    Возврат Новый Структура("rows", МассивСтрок);

КонецФункции

Функция ОписаниеМетаданных(Имя)

    Объект = Метаданные.НайтиПоПолномуИмени(Имя);
    Если Объект = Неопределено Тогда
        Возврат Новый Структура("error", "Не найдено: " + Имя);
    КонецЕсли;

    Реквизиты = Новый Массив;
    Для Каждого Реквизит Из Объект.Реквизиты Цикл
        Реквизиты.Добавить(Реквизит.Имя + " (" + ОписаниеТиповВСтроку(Реквизит.Тип) + ")");
    КонецЦикла;

    Возврат Новый Структура("name, attributes", Имя, Реквизиты);

КонецФункции

// Строка(ОписаниеТипов) нечитабельна — собираем имена типов вручную
Функция ОписаниеТиповВСтроку(ОписаниеТипов)

    ИменаТипов = Новый Массив;
    Для Каждого Тип Из ОписаниеТипов.Типы() Цикл
        ИменаТипов.Добавить(Строка(Тип));
    КонецЦикла;

    Возврат СтрСоединить(ИменаТипов, ", ");

КонецФункции
```

### Публикация

Конфигуратор: **Администрирование → Публикация на веб-сервере**.

- Включите публикацию HTTP-сервисов (галочка), имя публикации, например `erp`.
- Веб-сервер: Apache 2.4 или IIS (для Linux — Apache).
- **Обязательно**: в свойствах публикации включите Basic-аутентификацию, HTTPS — по возможности.

После публикации сервис доступен по адресу вида:

```
https://сервер/erp/hs/mcp/execute
```

Проверьте его до того, как идти дальше:

```bash
curl -u mcp_service:пароль -X POST https://сервер/erp/hs/mcp/execute \
  -H "Content-Type: application/json" \
  -d '{"operation":"query","query":"ВЫБРАТЬ ПЕРВЫЕ 5 Наименование ИЗ Справочник.Номенклатура"}'
```

Если получаете JSON со строками — сторона 1С готова.

## Шаг 2 — MCP-сервер на Python

### Подготовка окружения

```bash
mkdir mcp-1c && cd mcp-1c
uv init          # или: python -m venv .venv && .venv\Scripts\activate
uv add fastmcp httpx
```

`fastmcp` — самый быстрый способ написать сервер; `httpx` — HTTP-клиент.

### Код сервера — `server.py`

```python
import base64
import os

import httpx
from fastmcp import FastMCP

BASE_URL = os.environ["MCP_1C_URL"]       # https://сервер/erp/hs/mcp/execute
USER     = os.environ["MCP_1C_USER"]
PASSWORD = os.environ["MCP_1C_PASSWORD"]

auth_header = "Basic " + base64.b64encode(
    f"{USER}:{PASSWORD}".encode()
).decode()

mcp = FastMCP("1c-database")


async def call_1c(payload: dict) -> dict:
    """Вызов HTTP-сервиса 1С. Ошибки пробрасываем как текст ИИ-клиенту."""
    async with httpx.AsyncClient(verify=True, timeout=60) as client:
        r = await client.post(
            BASE_URL,
            json=payload,
            headers={"Authorization": auth_header,
                     "Content-Type": "application/json"},
        )
        r.raise_for_status()
        return r.json()


@mcp.tool
async def run_query(query: str, params: dict | None = None) -> str:
    """Выполнить запрос 1С (язык запросов 1С) и вернуть строки.

    Args:
        query: Текст запроса, например 'ВЫБРАТЬ ПЕРВЫЕ 10 Наименование ИЗ Справочник.Номенклатура'
        params: Параметры запроса, например {"Ссылка": "uuid-..."}
    """
    data = await call_1c({"operation": "query", "query": query, "params": params})
    if "error" in data:
        return f"Ошибка 1С: {data['error']}"
    rows = data["rows"]
    if not rows:
        return "Запрос вернул 0 строк."
    # Ограничиваем размер ответа, чтобы не переполнить контекст модели
    return f"Строк: {len(rows)}\n" + "\n".join(str(r) for r in rows[:100])


@mcp.tool
async def get_metadata(name: str) -> str:
    """Получить описание объекта метаданных 1С (реквизиты и их типы).

    Args:
        name: Полное имя, например 'Справочник.Номенклатура' или 'Документ.РеализацияТоваровУслуг'
    """
    data = await call_1c({"operation": "metadata", "name": name})
    if "error" in data:
        return f"Ошибка: {data['error']}"
    return f"{data['name']}\n" + "\n".join(data["attributes"])


if __name__ == "__main__":
    mcp.run()   # транспорт stdio — для десктопных клиентов
```

Три важные детали:

1. **Docstring'и и аннотации типов — это то, что видит модель.** Пишите их содержательно: именно по ним LLM решает, какой инструмент вызвать и с какими аргументами.
2. **Ограничивайте объём возвращаемых данных** (`rows[:100]`, усечение длинных строк). База 1С легко вернёт 100 000 строк и забьёт контекст модели.
3. **Ограничивайте и сторону 1С** — время выполнения и число строк. Тогда даже неосторожный запрос не «повесит» базу.

### Переменные окружения

Файл `.env` (или системные переменные — их удобнее задавать в конфиге клиента, см. шаг 3):

```
MCP_1C_URL=https://сервер/erp/hs/mcp/execute
MCP_1C_USER=mcp_service
MCP_1C_PASSWORD=...
```

### Проверка через MCP Inspector

Не подключайте сервер к клиенту сразу — сначала проверьте его изолированно:

```bash
# проще всего — командой официального Python-SDK
mcp dev server.py

# если пользуетесь только FastMCP — его собственной командой
fastmcp dev server.py

# либо напрямую Inspector
npx @modelcontextprotocol/inspector uv run server.py
```

Откроется веб-интерфейс: нажмите Connect → Tools → вызовите `run_query` с тестовым запросом. Если видите JSON-результат из 1С — сервер работает.

## Шаг 3 — подключение к ИИ-клиенту

Смысл конфигурации у всех клиентов один: какую команду запустить и какие переменные окружения передать. Отличаются только файл и обёртка. Типовая (универсальная) запись stdio-сервера:

```json
{
  "mcpServers": {
    "1c-database": {
      "command": "uv",
      "args": ["--directory", "C:/путь/к/mcp-1c", "run", "server.py"],
      "env": {
        "MCP_1C_URL": "https://сервер/erp/hs/mcp/execute",
        "MCP_1C_USER": "mcp_service",
        "MCP_1C_PASSWORD": "..."
      }
    }
  }
}
```

Где лежит этот файл и как называется ключ верхнего уровня:

| Клиент | Файл | Ключ |
|---|---|---|
| Claude Desktop | `claude_desktop_config.json` | `mcpServers` |
| Cursor | `.cursor/mcp.json` (проект) или `~/.cursor/mcp.json` | `mcpServers` |
| Cline / Roo | настройки MCP в панели расширения | `mcpServers` |
| VS Code (Copilot) | `.vscode/mcp.json` | `servers` |
| opencode | `opencode.json` | `mcp` |

У VS Code и opencode форма записи отличается. Так выглядит блок для opencode:

```json
{
  "mcp": {
    "1c-database": {
      "type": "local",
      "command": ["uv", "--directory", "C:/путь/к/mcp-1c", "run", "server.py"],
      "environment": {
        "MCP_1C_URL": "https://сервер/erp/hs/mcp/execute",
        "MCP_1C_USER": "mcp_service",
        "MCP_1C_PASSWORD": "..."
      }
    }
  }
}
```

После перезапуска клиента сервер появится в списке, а его инструменты (`run_query`, `get_metadata`) — в распоряжении модели. Точный формат для конкретного клиента всегда сверяйте с его документацией: ключи могут меняться между версиями.

## Безопасность — обязательно

- **Отдельная учётка с минимальными правами.** Роль только на чтение нужных справочников/документов. Никогда не подключайте ИИ под администратором.
- **Read-only по умолчанию.** Первая версия сервера должна уметь только `ВЫБРАТЬ`. Инструменты записи (`СоздатьДокумент`, `ПровестиДокумент`) добавляйте осознанно, с явными ограничениями и подтверждением в клиенте.
- **Произвольный запрос = риск.** Инструмент `run_query` выполняет любой текст запроса — поэтому он безопасен ровно настолько, насколько ограничены права пользователя `mcp_service` в 1С.
- **HTTPS.** Пароль передаётся в Basic-заголовке каждый вызов — без TLS он виден в сети.
- **Не коммитьте пароли.** Храните их в переменных окружения клиента, не в `server.py` и не в git.

## Куда развивать

Когда базовый вариант работает, естественные следующие инструменты:

- **`list_objects`** — перечислить справочники/документы конфигурации (модель сама найдёт нужное имя объекта через `get_metadata`).
- **`read_object`** — прочитать объект по ссылке/UUID с реквизитами и табличными частями.
- **`call_method`** — вызвать конкретные серверные методы 1С, добавив на стороне шлюза белый список разрешённых операций.
- **Запись** — создание документов через структурированный JSON, с валидацией и проверкой блокировок на стороне 1С.

Суть архитектуры при этом не меняется: каждая новая возможность — это новая ветка `Если Операция = ...` в шлюзе 1С и новая `@mcp.tool`-функция в Python.

Стандартный интерфейс [OData](/glossary/#odata) — это [REST](/glossary/#rest) API, который платформа 1С генерирует автоматически: CRUD-операции (чтение, создание, изменение, удаление) по любым опубликованным справочникам, документам и регистрам. Код писать не нужно — только настроить публикацию.

Когда использовать: внешней системе нужен доступ к данным 1С по HTTP без разработки HTTP-сервисов. Когда не подходит: нужны произвольные запросы, вызов методов или сложная бизнес-логика — тогда см. шпаргалки про [MCP](/cheats/mcp-server-1c/) и [HTTP-сервис](/cheats/http-service-1c/).

## Словарик новичка

| Слово | Что значит простыми словами |
|---|---|
| **[REST API](/glossary/#rest-api)** | Способ обращаться к данным по обычным HTTP-адресам (GET — прочитать, POST — создать…) |
| **[CRUD](/glossary/#crud)** | Четыре базовые операции: Create (создать), Read (прочитать), Update (изменить), Delete (удалить) |
| **Сущность** | Объект 1С, открытый через OData: справочник, документ, регистр |
| **[GUID](/glossary/#guid) (ссылка)** | Уникальный идентификатор объекта в базе (длинный код вида `8e7c…-…`), аналог «номера» записи |
| **[ETag / If-Match](/glossary/#etag)** | «Отпечаток» версии записи для защиты от одновременной правки; `If-Match: *` — «меняй что угодно» |
| **`$filter`, `$select`…** | Служебные параметры адреса: отбор, выбор полей, лимит строк |
| **Basic-аутентификация** | Логин и пароль, которые клиент присылает в каждом запросе |

## Настройка за 3 шага

1. **Пользователь.** Отдельная учётка латиницей (например, `odata_service`) с правами на чтение/запись нужных объектов. Кириллица в имени = Basic-аутентификация не заработает.
2. **Состав объектов.** Конфигуратор → **Администрирование → Стандартный интерфейс OData** → отметить галочками справочники/документы/регистры, которые публикуем. Не публикуйте всё подряд — каждый объект это открытый API.
3. **Публикация.** **Администрирование → Публикация на веб-сервере** → галочка **«Публиковать стандартный интерфейс OData»**. Для аутентификации — включите Basic в свойствах публикации.

Точка входа: `https://сервер/erp/odata/standard.odata` (`erp` — имя публикации базы, у вас может быть другое; `standard.odata` — фиксированная часть OData).

## Чтение: типовые запросы

Имя сущности строится из вида объекта и имени метаданных: `Справочник.Номенклатура` → `Catalog_Номенклатура`, `Документ.РеализацияТоваровУслуг` → `Document_РеализацияТоваровУслуг`. Имя метаданных берётся как есть (по-русски), а вид объекта — латинским словом (`Catalog_` — справочник, `Document_` — документ, `InformationRegister_` — регистр сведений).

```bash
# Первые 5 элементов справочника, только нужные поля, в JSON
curl -u odata_service:пароль \
  "https://сервер/erp/odata/standard.odata/Catalog_Номенклатура?\$top=5&\$select=Ref_Key,Description,Article&\$format=json"

# Фильтрация по значению
curl -u odata_service:пароль \
  "https://сервер/erp/odata/standard.odata/Catalog_Номенклатура?\$filter=Article eq 'А-001'&\$format=json"

# Один элемент по ключу: в скобках указывается GUID ссылки (берётся из Ref_Key в ответе)
curl -u odata_service:пароль \
  "https://сервер/erp/odata/standard.odata/Catalog_Номенклатура(guid='...')?\$format=json"

# Регистр сведений с отбором по периоду (v4: date-time в одинарных кавычках)
curl -u odata_service:пароль \
  "https://сервер/erp/odata/standard.odata/InformationRegister_ЦеныТоваров?\$filter=Period gt datetime'2026-01-01T00:00:00'&\$format=json"
```

Полезные параметры: `$filter`, `$select`, `$top`/`$skip` (постранично), `$orderby`, `$expand` (подтянуть табличные части и реквизиты-ссылки одним запросом), `$count=true` (получить число строк). Полное описание модели: `GET .../standard.odata/$metadata`.

## Запись: создание и изменение

```bash
# Создать элемент справочника — POST с телом JSON
curl -u odata_service:пароль -X POST \
  "https://сервер/erp/odata/standard.odata/Catalog_Номенклатура?\$format=json" \
  -H "Content-Type: application/json" \
  -d '{"Description": "Новый товар", "Article": "А-002"}'

# Изменить — PATCH, обязательно с If-Match (ETag)
curl -u odata_service:пароль -X PATCH \
  "https://сервер/erp/odata/standard.odata/Catalog_Номенклатура(guid='...')" \
  -H "Content-Type: application/json" -H "If-Match: *" \
  -d '{"Article": "А-003"}'
```

В ответ на создание (POST) платформа присылает объект целиком, включая поле **`Ref_Key`** — это и есть GUID новой записи: по нему дальше её читают, меняют и удаляют.

Платформа сама проведёт документ, если у него есть обработчик проведения, — по умолчанию документы при создании через OData **проводятся** (режим `Проведение` управляется полем `Posted`).

## Типовые грабли

- **401 Unauthorized** — имя пользователя или пароль кириллицей/с спецсимволами, либо Basic-аутентификация не включена в публикации.
- **404 на сущность** — объект не добавлен в состав стандартного интерфейса OData. Состав задаётся в Конфигураторе, либо программно `УстановитьСоставСтандартногоИнтерфейсаOData()` из внешнего соединения.
- **Регистр букв в URL** — имена сущностей и полей чувствительны: `Description`, а не `description`.
- **Windows-оболочка съедает `$`** — в bash экранируйте `\$filter`, в PowerShell используйте одинарные кавычки вокруг URL.
- **Тормоза на больших таблицах** — всегда ограничивайте `$top` и фильтруйте по индексированным полям; OData без ограничений прочитает таблицу целиком.
- **Версия протокола** — современные платформы (8.3.13+) отдают OData v4; старые — v3, где другой синтаксис фильтров (`startswith()` вместо `StartsWith`, даты без `datetime'...'`).

## OData vs HTTP-сервис

| | OData | HTTP-сервис |
|---|---|---|
| Настройка | Только галочки в Конфигураторе | Нужно писать обработчик |
| Операции | Только CRUD по объектам | Любая логика: запросы, методы, обмен |
| Формат | Стандартный REST/JSON, понятно любому разработчику | Свои контракты, нужно документировать |
| Безопасность | Права 1С на уровне объектов | Полностью под вашим контролем |

Если вы никогда не обращались к внешнему API из 1С — начните с первых трёх разделов: там объясняется, что вообще происходит и из каких частей состоит запрос. Дальше — по шагам, с кодом и проверкой на каждом этапе. Никакого опыта веб-разработки не требуется.

## Что такое «внешнее API» и зачем оно 1С

**[API](/glossary/#api)** — это программный интерфейс: набор «дверей», в которые одна программа может постучать, чтобы что-то узнать или сделать. Внешнее API есть у банков, маркетплейсов, сервисов доставки, Telegram, курсов валют — у любой системы, которая умеет общаться с другими.

1С умеет быть по обе стороны обмена:

- **исходящие запросы** — запрос уходит из 1С во внешнюю систему;
- **входящие запросы** — запрос приходит из внешней системы в 1С, и она его обрабатывает (см. [«Приём входящих через HTTP-сервис: свой REST с нуля»](/cheats/http-service-1c/)).

```
   1С  ──  HTTP-запрос (что и от кого нужно)  ──▶  Внешний сервис (API)
       ◀─  HTTP-ответ (данные или ошибка)     ──
```

Руками это выглядит так: зашли на сайт сервиса, скачали данные, занесли в 1С. Работает — пока данных мало. При потоке это рутина и ошибки. API позволяет 1С делать то же самое сама, по расписанию, без человека.

Типичные задачи: получить курсы валют и загрузить их в 1С, отправить СМС, забрать заказы с маркетплейса, выгрузить остатки на сайт, передать платёжку в банк.

## Что понадобится

- Сервер 1С (или регламентное задание) с **доступом в интернет** — запросы идут именно с сервера, а не с компьютера пользователя;
- адрес API и его **документация** — из неё берутся хост, путь (эндпоинт), метод и формат данных;
- **ключ или токен** — выданный сервисом «пропуск», если API не открытый;
- базовое понимание **JSON** — текстового формата, в котором данные ходят туда и обратно.

> **Важно.** Объект `HTTPСоединение` доступен только на сервере (и во внешнем соединении). В толстом клиенте его нет: запросы делают на сервере, а результат передают на клиент.

## Словарик новичка

Пять минут на эти слова сэкономят часы непонимания дальше.

| Слово | Что значит простыми словами |
|---|---|
| **API** | Набор «дверей», через которые одна программа общается с другой |
| **[HTTP / HTTPS](/glossary/#http)** | Правила, по которым идёт общение. HTTPS — то же, но зашифровано (TLS) |
| **Хост / сервер** | Адрес сервиса без протокола, например `api.example.com` |
| **[Эндпоинт](/glossary/#endpoint)** | Конкретный путь, «дверь», например `/v1/rates` |
| **[Метод](/glossary/#http-metod)** | Что мы хотим сделать: прочитать, создать, изменить, удалить |
| **Заголовок** | Служебная строка запроса: какое тело, какой токен, что хотим получить |
| **Тело запроса** | Основные данные, которые отправляем (обычно JSON) |
| **Код состояния** | Число в ответе: `200` — успех, `4xx` — наша ошибка, `5xx` — ошибка сервиса |
| **[JSON](/glossary/#json)** | Текстовый формат данных: `{"поле": "значение"}` |
| **[Токен](/glossary/#token)** | Пароль для программы. Сервис выдаёт его заранее, передаём в заголовке `Authorization` |
| **[Basic / Bearer](/glossary/#basic-auth)** | Способы авторизации. Basic — присылаем логин и пароль. Bearer — присылаем один токен («билет»): кто его предъявил, тот и допущен |
| **Таймаут** | Сколько секунд ждать ответ, прежде чем признать сервис недоступным |

## Как устроен один запрос

Запрос в 1С собирается из двух объектов:

1. **`HTTPЗапрос`** — что именно спрашиваем: адрес (путь), метод, заголовки, тело.
2. **`HTTPСоединение`** — куда идём: сервер, порт, при необходимости логин/пароль, прокси, таймаут.

Отправка — это вызов метода соединения, имя которого зависит от HTTP-метода. Соответствие такое:

| Что делаем | HTTP-метод | Метод 1С |
|---|---|---|
| Прочитать | `GET` | `Соединение.Получить(Запрос)` |
| Создать | `POST` | `Соединение.ОтправитьДляОбработки(Запрос)` |
| Заменить целиком | `PUT` | `Соединение.Записать(Запрос)` |
| Изменить частично | `PATCH` | `Соединение.Изменить(Запрос)` |
| Удалить | `DELETE` | `Соединение.Удалить(Запрос)` |
| Любой другой | — | `Соединение.ВызватьHTTPМетод(Метод, Запрос)` |

Возвращается **`HTTPОтвет`**: у него есть `КодСостояния`, `Заголовки` и тело (строка, двоичные данные или поток).

## Шаг 1. Простейший GET-запрос

Самый частый случай: получить данные и разобрать JSON. Для HTTPS пятым параметром передаём защищённое соединение.

```bsl
Функция ПолучитьКурсыВалют() Экспорт

    // Куда идём: сервер, порт, логин/пароль (пусто), прокси (пусто),
    // таймаут в секундах, защищённое соединение для https
    Соединение = Новый HTTPСоединение(
        "api.example.com",                   // сервер (без https://)
        443,                                 // порт: 443 для https, 80 для http
        , ,                                  // пользователь, пароль
        , 10,                                // таймаут, сек
        Новый ЗащищенноеСоединениеOpenSSL);  // для https

    // Что спрашиваем: путь и заголовки
    Запрос = Новый HTTPЗапрос("/v1/rates?currency=USD");
    Запрос.Заголовки.Вставить("Accept", "application/json");

    // Отправляем GET
    Ответ = Соединение.Получить(Запрос);

    // Проверяем код состояния, а не «выбросило исключение или нет»
    Если Ответ.КодСостояния <> 200 Тогда
        ВызватьИсключение "HTTP " + Ответ.КодСостояния
            + ": " + Ответ.ПолучитьТелоКакСтроку();
    КонецЕсли;

    // Разбираем тело ответа как JSON
    Чтение = Новый ЧтениеJSON;
    Чтение.УстановитьСтроку(Ответ.ПолучитьТелоКакСтроку());
    Данные = ПрочитатьJSON(Чтение, Ложь);
    Чтение.Закрыть();

    Возврат Данные;

КонецФункции
```

`ПрочитатьJSON(Чтение, Ложь)` — второй параметр `Ложь` означает «получить структуру данных как есть» (по умолчанию 1С перевела бы всё в соответствие).

## Шаг 2. POST-запрос с JSON и Bearer-токеном

POST отправляет данные наружу: создать заказ, отправить сообщение, загрузить остаток.

```bsl
Функция ОтправитьЗаказ(ЗаказJSON) Экспорт

    Соединение = Новый HTTPСоединение("api.example.com", 443, , , , 10,
        Новый ЗащищенноеСоединениеOpenSSL);

    Запрос = Новый HTTPЗапрос("/v1/orders");
    Запрос.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");
    Запрос.Заголовки.Вставить("Authorization", "Bearer " + ТокенAPI());

    // Тело можно задать строкой или двоичными данными
    Запрос.УстановитьТелоИзСтроки(ЗаказJSON, КодировкаТекста.UTF8);

    Ответ = Соединение.ОтправитьДляОбработки(Запрос);

    Возврат Ответ.КодСостояния;

КонецФункции
```

Заголовок `Content-Type` сообщает сервису, в каком формате тело (`application/json`), а `charset=utf-8` — что текст в UTF-8.

Про `Authorization` и `Bearer` отдельно: `Bearer` (англ. «носитель») — это способ авторизации, при котором доступ даёт сам токен, как билет на входе. Кто предъявил действительный токен — тот и допущен, без логина и пароля. Поэтому токен равносилен паролю: его держат в тайне и передают только по HTTPS.

## Шаг 3. Собираем тело запроса (JSON)

Тело POST-запроса (Шаг 2) — это просто текст в формате JSON, например `{"amount":100,"currency":"RUB"}`. Получить эту строку можно двумя способами.

**Способ 1 — написать строку вручную.** Годится, когда JSON короткий:

```bsl
ТелоЗапроса = "{""amount"":100,""currency"":""RUB""}";
// помните: внутри строки 1С кавычка удваивается — "" это одна "
```

**Способ 2 — заполнить структуру и превратить её в JSON.** Надёжнее, когда полей много или они берутся из базы: 1С сама расставит кавычки, скобки и запятые, ошибиться в разметке JSON негде.

```bsl
// Обычная структура 1С: имя поля → значение
Заказ = Новый Структура;
Заказ.Вставить("amount", 100);
Заказ.Вставить("currency", "RUB");

// Превращаем структуру в строку JSON
Запись = Новый ЗаписьJSON;
Запись.УстановитьСтроку(Новый НастройкиСериализацииJSON);
ЗаписатьJSON(Запись, Заказ);
ТелоЗапроса = Запись.Закрыть();   // получилось {"amount":100,"currency":"RUB"}
```

Оба способа дают одну и ту же строку. Дальше она уходит в `Запрос.УстановитьТелоИзСтроки(ТелоЗапроса, КодировкаТекста.UTF8)` из Шага 2.

## Шаг 4. Авторизация Basic

Если сервис использует логин и пароль, 1С сама сформирует заголовок `Authorization: Basic ...` — достаточно передать их в конструктор соединения.

```bsl
Соединение = Новый HTTPСоединение("api.example.com", 443,
    "логин", "пароль", , 10, Новый ЗащищенноеСоединениеOpenSSL);
```

## Параметры соединения

Полный конструктор `HTTPСоединение` (после сервера все параметры необязательны):

| Параметр | Смысл |
|---|---|
| `Сервер` | Адрес без протокола: `api.example.com` |
| `Порт` | 443 для HTTPS, 80 для HTTP (по умолчанию подставляется сам) |
| `Пользователь`, `Пароль` | Для Basic-авторизации |
| `Прокси` | Объект `ИнтернетПрокси`, если выход в интернет через прокси |
| `Таймаут` | Секунды ожидания; `0` — ждать бесконечно (так делать не стоит) |
| `ЗащищенноеСоединение` | `Новый ЗащищенноеСоединениеOpenSSL` для HTTPS |
| `ИспользоватьАутентификациюОС` | Для доменной аутентификации (NTLM/Negotiate) |

## Типовые грабли

- **Таймаут обязателен.** Без него зависший внешний сервер подвесит сеанс 1С (или регламентное задание) надолго. Ставьте 10–30 секунд.
- **Кодировка тела.** `УстановитьТелоИзСтроки(Строка)` без указания кодировки может отправить не в UTF-8 — всегда передавайте `КодировкаТекста.UTF8` явно. И дублируйте это в `Content-Type` через `charset=utf-8`.
- **TLS-ошибки на Linux.** Серверу 1С под Linux нужен пакет корневых сертификатов (`ca-certificates`), иначе `ЗащищенноеСоединениеOpenSSL` не установит соединение. Свои CA-сертификаты подключаются через `СертификатыУдостоверяющихЦентровOpenSSL`.
- **Прокси.** В корпоративных сетях без прокси наружу не выйти — передайте `ИнтернетПрокси` пятым параметром конструктора.
- **Коды ответа.** `200` — успех; `4xx` — ваша ошибка (проверьте тело, там обычно JSON с описанием); `5xx` — ошибка сервера (стоит повторить запрос позже). Всегда проверяйте `КодСостояния`, не полагайтесь на отсутствие исключений.
- **Повторы (ретраи).** При `5xx` или коде `429` (слишком много запросов) не «долбите» сервис в цикле: выждите паузу и повторите ограниченное число раз. Лимиты запросов описаны в документации API.
- **Большие файлы.** Не читайте тело в строку: `Ответ.ПолучитьТелоКакДвоичныеДанные()` или поток (`Ответ.ПолучитьТелоКакПоток()`). При отправке — `УстановитьТелоИзДвоичныхДанных` и `УстановитьИмяФайлаТела`.
- **Безопасность токенов.** Токены храните в безопасном хранилище (`ЗащищенноеХранилищеДанных`), не в константах и не в коде. И не логируйте заголовок `Authorization`.
- **Один сервер — одно соединение.** Объект `HTTPСоединение` можно переиспользовать для нескольких запросов к тому же серверу — не создавайте его заново на каждый вызов.
- **Асинхронные методы на клиенте.** Начиная с 8.3.21 на клиенте обычные методы `Получить`, `ОтправитьДляОбработки` и т.д. устарели — там нужны `...Асинх` и `Ждать`. На сервере используйте обычные методы.

Минимальный бот на 1С — это два куска: **отправка** (обычный POST на [Telegram API](/glossary/#telegram-api) из кода 1С) и **приём** ([вебхук](/glossary/#webhook) через HTTP-сервис 1С либо long polling из [регламентного задания](/glossary/#reglamentnoe-zadanie)).

## Подготовка

1. Создайте бота у [@BotFather](https://t.me/BotFather), получите токен вида `123456:AA...`.
2. Для вебхука нужен **HTTPS с валидным сертификатом** — Telegram не принимает самоподписанные. Вебхук вешается на опубликованный HTTP-сервис 1С.
3. Токен храните в безопасном хранилище, не в коде.

## Отправка сообщения

Токен бота храните в безопасном месте и читайте функцией-обёрткой (ниже — `ТокенБота()`; это **ваша** функция: константа, регистр или БезопасноеХранилище). В код токен не вписывайте.

```bsl
Процедура ОтправитьСообщениеTelegram(ЧатИД, Текст) Экспорт

    Соединение = Новый HTTPСоединение("api.telegram.org", 443, , , , 15,
        Новый ЗащищенноеСоединениеOpenSSL);

    Запрос = Новый HTTPЗапрос("/bot" + ТокенБота() + "/sendMessage");
    Запрос.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");

    Тело = Новый Структура;
    Тело.Вставить("chat_id", ЧатИД);
    // Обычный текст без разметки — отправится всегда.
    Тело.Вставить("text", Текст);

    Запись = Новый ЗаписьJSON;
    Запись.УстановитьСтроку(Новый НастройкиСериализацииJSON);
    ЗаписатьJSON(Запись, Тело);
    Запрос.УстановитьТелоИзСтроки(Запись.Закрыть(), КодировкаТекста.UTF8);

    Ответ = Соединение.ОтправитьДляОбработки(Запрос);
    Если Ответ.КодСостояния <> 200 Тогда
        ЗаписьЖурналаРегистрации("Telegram", УровеньЖурналаРегистрации.Ошибка,,,
            Ответ.ПолучитьТелоКакСтроку());
    КонецЕсли;

КонецПроцедуры

// Экранирование спецсимволов HTML. Сначала заменяем "&", потом "<" и ">".
Функция ЭкранироватьHTML(Текст)
    Результат = СтрЗаменить(Текст, "&", "&amp;");
    Результат = СтрЗаменить(Результат, "<", "&lt;");
    Результат = СтрЗаменить(Результат, ">", "&gt;");
    Возврат Результат;
КонецФункции
```

> **Разметка (жирный, курсив, ссылки).** Чтобы отправить текст с HTML-разметкой, добавьте в тело `Тело.Вставить("parse_mode", "HTML");` и используйте теги (`<b>`, `<i>`, `<a href="...">`). Но тогда **любой пользовательский текст нужно прогнать через `ЭкранироватьHTML()`** — иначе символы `<`, `>`, `&` в тексте сломают запрос, и Telegram вернёт ошибку.

## Приём: вариант 1 — вебхук (рекомендуется)

Создайте HTTP-сервис `TelegramBot`, корневой URL `tg`, шаблон `/notify/<секретный-хвост>/*` (секрет в пути — простая защита от чужих запросов). Telegram сам присылает входящие сообщения:

```bash
# одноразовая настройка вебхука (выполняется где угодно)
curl "https://api.telegram.org/bot<ТОКЕН>/setWebhook?url=https://сервер/erp/hs/tg/notify/секретный-хвост"
```

Обработчик POST парсит уведомление и быстро отвечает `200` (Telegram ретраит, если не ответить за несколько секунд):

```bsl
Функция NotifyPOST(Запрос)

    Ответ = Новый HTTPСервисОтвет(200);

    Чтение = Новый ЧтениеJSON;
    Чтение.УстановитьСтроку(Запрос.ПолучитьТелоКакСтроку());
    Обновление = ПрочитатьJSON(Чтение, Ложь);
    Чтение.Закрыть();

    Сообщение = Обновление.Получить("message");
    Если Сообщение <> Неопределено Тогда
        Чат = Сообщение.Получить("chat");
        ЧатИД = Чат.Получить("id");
        Текст = Сообщение.Получить("text");   // для фото/стикеров text = Неопределено

        // Ваша логика: команды, ответы пользователю, запись в базу...
        Если Текст <> Неопределено Тогда
            ОтправитьСообщениеTelegram(ЧатИД, "Принято: " + Текст);
        КонецЕсли;
    КонецЕсли;

    Возврат Ответ;

КонецФункции
```

## Приём: вариант 2 — long polling (без HTTPS и вебхуков)

Регламентное задание раз в N секунд вызывает `getUpdates` и обрабатывает сообщения с `update_id` больше последнего обработанного (offset). Плюс: не нужен белый IP/сертификат. Минус: задержка на интервал задания и «ручной» контроль offset — храните его в константе или регистре.

```bsl
// Таймаут соединения (40) должен быть больше timeout в запросе (25), иначе оборвётся раньше ответа.
Соединение = Новый HTTPСоединение("api.telegram.org", 443, , , , 40,
    Новый ЗащищенноеСоединениеOpenSSL);

Запрос = Новый HTTPЗапрос("/bot" + ТокенБота()
    + "/getUpdates?timeout=25&offset=" + (ПоследнийUpdateID + 1));
Ответ = Соединение.Получить(Запрос);   // ждёт до 25 секунд новых сообщений
```

## Типовые грабли

- **Вебхук не ставится** — Telegram вернёт ошибку, если сертификат самоподписанный, URL без HTTPS или хост недоступен из интернета. `getWebhookInfo` показывает последнюю ошибку доставки.
- **Повторные уведомления.** Telegram ретраит недоставленные update — делайте обработку идемпотентной (по `update_id`).
- **Лимиты.** ~30 сообщений в секунду на бота; при рассылках добавьте паузы и очередь (см. шпаргалку про [исходящую очередь](/cheats/outgoing-queue-1c/)).
- **TLS из 1С.** Для `api.telegram.org` на Linux-сервере 1С нужны корневые сертификаты, иначе исходящие HTTPS-запросы падают.
- **Не светите токен.** Любой, у кого есть токен, управляет ботом. Токен всегда уходит в адресе запроса (`/bot<токен>/…`), поэтому не логируйте полные URL и не храните токен в коде — только в защищённом хранилище.

Наивная интеграция «при проведении документа — сразу HTTP-запрос во внешний сервис» рано или поздно теряет данные: внешний API недоступен, сеть моргнула, у пользователя не хватило прав. Паттерн [исходящей очереди](/glossary/#ochered) решает это: **событие только записывает сообщение в очередь, доставкой занимается отдельное [фоновое задание](/glossary/#fonovoe-zadanie) с ретраями**.

> **Почему не отправлять сразу на месте события:** запись в очередь быстрая и не зависит от доступности внешней системы; ошибки доставки не мешают работе пользователей; есть мониторинг — всегда видно, что не отправлено и почему.

## Структура хранения

Регистр сведений **ОчередьИсходящихСообщений** (независимый, периодический не нужен):

| Поле | Тип | Смысл |
|---|---|---|
| Идентификатор | УникальныйИдентификатор | Ключ сообщения, дублируется в тело (идемпотентность) |
| Адрес | Строка | URL/операция получателя |
| Тело | Строка (неограниченная) | JSON сообщения |
| Статус | Перечисление/строка | КОтправке, Отправлено, Ошибка |
| ДатаСоздания | Дата | Для сортировки и контроля старья |
| ДатаВзятия | Дата | Когда сообщение взято в работу (контроль зависших) |
| ЧислоПопыток | Число | Счётчик ретраев |
| ПоследняяОшибка | Строка | Что вернул внешний сервис |

## Запись в очередь — на месте события

```bsl
Процедура ПоставитьВОчередь(Адрес, СтруктураСообщения) Экспорт

    Если СтруктураСообщения.Свойство("ИдентификаторСообщения") Тогда
        СтруктураСообщения.Удалить("ИдентификаторСообщения");
    КонецЕсли;
    СтруктураСообщения.Вставить("ИдентификаторСообщения", Новый УникальныйИдентификатор);

    ЗаписьJSON = СериализоватьВJSON(СтруктураСообщения); // ЗаписьJSON → строка

    МенеджерЗаписи = РегистрыСведений.ОчередьИсходящихСообщений.СоздатьМенеджерЗаписи();
    МенеджерЗаписи.Идентификатор = СтруктураСообщения.ИдентификаторСообщения;
    МенеджерЗаписи.Адрес         = Адрес;
    МенеджерЗаписи.Тело          = ЗаписьJSON;
    МенеджерЗаписи.Статус        = Перечисления.СтатусыСообщений.КОтправке;
    МенеджерЗаписи.ДатаСоздания  = ТекущаяДатаСеанса();
    МенеджерЗаписи.ЧислоПопыток  = 0;
    МенеджерЗаписи.Записать(Истина);

КонецПроцедуры
```

## Доставка — [регламентное задание](/glossary/#reglamentnoe-zadanie)

Запускается каждые 1–5 минут. Важно: **пометить сообщения «в работе» до отправки** (иначе два сеанса задания возьмут одно сообщение дважды). Простой способ — отдельный статус «ВОбработке» с датой взятия, сбрасываемый по таймауту.

```bsl
Процедура ДоставитьСообщения() Экспорт

    // 1. Возвращаем в очередь «зависшие» (задание упало, статус не сбросился)
    СброситьЗависшие();

    // 2. Берём пачку «КОтправке» и помечаем «ВОбработке» под блокировкой,
    //    чтобы два сеанса задания не взяли одно сообщение дважды
    Взятые = ВзятьПачкуВРаботу();

    Для Каждого Идентификатор Из Взятые Цикл

        Данные = ДанныеСообщения(Идентификатор);

        Попытка
            КодОтвета = ОтправитьHTTP(Данные.Адрес, Данные.Тело);
            Успех = (КодОтвета >= 200 И КодОтвета < 300);
            Ошибка = ?(Успех, "", "HTTP " + КодОтвета);
        Исключение
            Успех   = Ложь;
            Ошибка  = ОписаниеОшибки();
        КонецПопытки;

        ОбновитьСтатус(Идентификатор, Успех, Ошибка, Данные.ЧислоПопыток);

    КонецЦикла;

КонецПроцедуры

// Выбирает до 50 сообщений «КОтправке» и переводит их в «ВОбработке»
// в одной транзакции.
// ВНИМАНИЕ: здесь взята исключительная блокировка всего регистра — это упрощение
// для наглядности. В нагруженной системе такая блокировка избыточна (см. стандарты
// #std659, #std460): сужайте область блокировки до конкретных записей
// (ЭлементБлокировки.УстановитьЗначение("Идентификатор", ...)) или до источника,
// чтобы не сериализовать параллельные сеансы задания.
Функция ВзятьПачкуВРаботу() Экспорт

    Идентификаторы = Новый Массив;

    НачатьТранзакцию();
    Попытка

        Блокировка = Новый БлокировкаДанных;
        ЭлементБлокировки = Блокировка.Добавить("РегистрСведений.ОчередьИсходящихСообщений");
        ЭлементБлокировки.Режим = РежимБлокировкиДанных.Исключительный;
        Блокировка.Заблокировать();

        Запрос = Новый Запрос(
            "ВЫБРАТЬ ПЕРВЫЕ 50
            |   Сообщения.Идентификатор КАК Идентификатор
            |ИЗ РегистрСведений.ОчередьИсходящихСообщений КАК Сообщения
            |ГДЕ Сообщения.Статус = ЗНАЧЕНИЕ(Перечисление.СтатусыСообщений.КОтправке)
            |УПОРЯДОЧИТЬ ПО Сообщения.ДатаСоздания");
        Выборка = Запрос.Выполнить().Выбрать();

        Пока Выборка.Следующий() Цикл
            Менеджер = РегистрыСведений.ОчередьИсходящихСообщений.СоздатьМенеджерЗаписи();
            Менеджер.Идентификатор = Выборка.Идентификатор;
            Менеджер.Прочитать();
            Менеджер.Статус     = Перечисления.СтатусыСообщений.ВОбработке;
            Менеджер.ДатаВзятия = ТекущаяДатаСеанса();
            Менеджер.Записать(Истина);

            Идентификаторы.Добавить(Выборка.Идентификатор);
        КонецЦикла;

        ЗафиксироватьТранзакцию();

    Исключение
        ОтменитьТранзакцию();
        ВызватьИсключение;
    КонецПопытки;

    Возврат Идентификаторы;

    Пока Выборка.Следующий() Цикл
        ОбновитьСтатус(Выборка.Идентификатор, Ложь,
            "Таймаут обработки", Выборка.ЧислоПопыток);
    КонецЦикла;

КонецПроцедуры

Процедура ОбновитьСтатус(Идентификатор, Успех, Ошибка, ЧислоПопыток)

    Менеджер = РегистрыСведений.ОчередьИсходящихСообщений.СоздатьМенеджерЗаписи();
    Менеджер.Идентификатор = Идентификатор;
    Менеджер.Прочитать();

    Если Успех Тогда
        Менеджер.Статус = Перечисления.СтатусыСообщений.Отправлено;

    КонецЕсли;
    Менеджер.Записать(Истина);
```

## Правила, без которых очередь не работает

- **[Идемпотентность](/glossary/#idempotentnost).** Отправка может задвоиться (упало соединение после того, как сервер уже обработал запрос). Поэтому в теле всегда ездит `ИдентификаторСообщения`, а принимающая сторона игнорирует повторные идентификаторы.
- **Ретраи с ограничением.** Без лимита попыток «мёртвое» сообщение будет гоняться вечно и грузить журнал. После 10 попыток — статус «Ошибка» и разбор человеком.
- **Порядок не гарантирован.** Если важна последовательность событий одного объекта, добавьте в сообщение дату/номер события и обрабатывайте на приёмнике, либо шлите объект целиком, а не дельты.
- **Блокировка.** Пачка берётся в транзакции с блокировкой регистра. Исключительная блокировка всего регистра — наглядное упрощение; в нагруженной системе её стоит сузить до конкретных записей/источника, иначе параллельные сеансы задания будут ждать друг друга (см. #std659, #std460).
- **Мониторинг.** Типовой отчёт по регистру: сколько в статусе «КОтправке» старше часа, сколько «Ошибок» — и оповещение в Telegram (см. шпаргалку про [бота](/cheats/telegram-bot-1c/)).
- **Не кладите в очередь большие тела.** Прикрепления и файлы лучше передавать по ссылке, а не base64 в регистре.
- **Очистка.** Периодическая процедура удаляет «Отправлено» старше N дней, иначе регистр растёт бесконечно.

Этот же паттерн — основа для ботов (очередь исходящих сообщений Telegram), обменов через шину и любых «fire-and-forget» уведомлений из 1С.

Обновить «чистую» типовую конфигурацию просто — загрузить файл поставки. Боль начинается, когда конфигурация доработана: обновление может стереть доработки или, наоборот, потянуть за собой неработающую смесь старого и нового. Шпаргалка описывает путь через «Сравнение, объединение с конфигурацией из файла поставки».

## Словарик новичка

| Слово | Что значит простыми словами |
|---|---|
| **[Поставщик](/glossary/#postavshik)** | Разработчик типовой (фирма «1С» или партнёр), выпускающий новые версии |
| **Поддержка / замок** | Режим, определяющий, можно ли менять объект и как объединять его при обновлении |
| **Реструктуризация** | Перестройка таблиц базы под новую структуру метаданных (самая долгая часть обновления) |
| **Расширение** | Отдельный «слой» с доработками поверх типовой; при обновлении его не объединяют |
| **Хранилище конфигурации** | Хранилище версий (аналог Git), куда разработчики фиксируют доработки |
| **`.cf` / `.cfu` / `.dt`** | `.cf` — полная конфигурация, `.cfu` — файл обновления, `.dt` — выгрузка базы (бэкап) |
| **F7** | Горячая клавиша «Обновить конфигурацию базы данных» в Конфигураторе |

## Чек-лист до обновления

- **Резервная копия** (выгрузка `.dt` или копия кластера) — обновление с реструктуризацией откатывается только так.
- **Платформа совместима** с новой версией конфигурации: минимальная версия платформы указана в описании обновления (файл с информацией о поставке на диске обновления). Сначала обновляем платформу, потом конфигурацию, потом ИБ.
- **Все пользователи вышли**, сеансы в кластере завершены (монитор активных сеансов).
- **Доработки зафиксированы**: если ведёте конфигурацию в хранилище/файлах — убедитесь, что всё закоммичено, чтобы после обновления было с чем сравнить.
- **Прочитано описание обновления** — какие объекты затронуты, есть ли реструктуризация и дополнительная обработка данных (запуск после обновления).
- **Расширения инвентаризированы** — список используемых расширений под рукой.

## Механика обновления

### Вариант 1 — доработки в расширениях (лучший случай)

Если все доработки сделаны расширениями, основная конфигурация «чистая»: просто загрузите файл поставки (`Администрирование → Обновление конфигурации → Загрузить файл обновления`) и обновите БД. Расширения при этом не трогаются — но их надо протестировать: реквизиты и модули, к которым они прицеплены, могли измениться.

### Вариант 2 — доработки в основной конфигурации

1. **Конфигуратор → Конфигурация → Поддержка → Настройка поддержки**: проверьте правила. По умолчанию объекты поставщика стоят как **«Объект поставщика, не редактируется»**. Чтобы править объект, ему (точнее — только изменяемой части, например форме или модулю) ставят **«Объект поставщика редактируется с сохранением поддержки»** (замок «приоткрыт»). Меняйте правило **точечно**: где доработок нет — оставляйте «не редактируется», так обновление проходит проще. Чтобы менять правила поддержки, в хранилище захватывают только **корень конфигурации**, а не сами объекты. Если объект снят с поддержки («Не поддерживается»), объединение с поставкой для него не сработает — верните правило или осознанно принимайте ручное сопровождение.
2. **Конфигурация → Сравнить, объединить с конфигурацией из файла** → выберите `.cf` новой версии.
3. Откроется окно сравнения. Ключевая колонка — **«Объединение»**:
   - для **изменённых поставщиком** объектов — «Собственная разработка + новая конфигурация поставщика» (объединение);
   - для **не изменённых** — из поставки;
   - ваши объекты (новые, не из поставщика) — «Собственная разработка».
4. Кнопкой **«Действия → Установить по умолчанию»** обычно получают правильный расклад; дальше просмотрите красные строки (конфликтные) вручную — там, где правился один и тот же код, объединение предложит выбрать вариант.
5. **Выполнить объединение** → просмотреть итог → **F7** (обновить конфигурацию БД).

### Вариант 3 — конфигурация сильно переписана

Если доработки массово и правила поддержки поломаны, честнее собрать новую базу: обновить чистую копию типовой и **перенести доработки** вручную/по списку. Дольше единожды, зато потом конфигурация снова обновляется по варианту 1–2 без подвигов.

## Чек-лист после обновления

- Конфигурация БД обновлена, ошибок реструктуризации нет.
- Запущено **тестирование и исправление** (см. шпаргалку про [бэкапы и сопровождение ИБ](/cheats/backup-cli-1c/)).
- Выполнены **дополнительные обработки перехода** из описания обновления (пересчёты, перезаполнение реквизитов). Если менялись метаданные, проверьте, что отработал обработчик обновления данных (универсальный механизм «Обновление версии ИБ»).
- Обновлены/проверены **расширения**: отчёты, печатные формы, заимствованные объекты открываются и работают.
- Смоук-тест по сценарию пользователя: создать документ, провести, распечатать, сформировать ключевой отчёт.
- Доработки закоммичены в хранилище/Git (фиксация состояния «после обновления»).
- Мониторинг пару дней: журнал регистрации на ошибки, обращения пользователей.

## Типовые грабли

> **«Объект не актуален» при обновлении БД** — базу обновляли из другого сеанса/копии или прервали реструктуризацию. Восстанавливать из бэкапа и повторять.
>
> **Потерялись доработки** — для конфликтных объектов выбрали «из поставки» вместо объединения. Лечится только бэкапом: поэтому он первый пункт чек-листа.
>
> **Обновление висит часами** — для больших баз реструктуризация это нормально. Не прерывайте процесс и не убивайте сеанс: недоведённая реструктуризация — главная причина битых ИБ. Предварительно оценивайте время на копии базы.
>
> **Расширения отвалились** — обновление переименовало/удалило реквизиты, на которых стоят расширения. Проверяйте отчёт «Расширения конфигурации» и тестируйте до того, как пустить пользователей.
>
> **Конфликт расширения** — объекты и процедуры расширения называйте с префиксом расширения, а метод-расширение должен точно совпадать по описанию с расширяемым. Иначе после обновления расширение может не «подхватиться» или помешать объединению.
>
> **Поломана поддержка объектов** — правила выставлены «на весь объект» или потерян файл поддержки (`ParentConfigurations.bin`). Тогда объединение с поставкой не даёт применить изменения. Держите правила точечными и не снимайте объекты с поддержки «чтобы не мешало».
>
> **Порядок пропущен** — сначала платформа, затем конфигурация, затем данные. Обновление конфигурации на старой платформе даёт самые трудноотлаживаемые ошибки.

## Ключевая идея

Расширения — это способ перевести базу в «лучший случай»: типовая остаётся чистой, обновления ставятся за минуты, а доработки живут отдельно и переносятся между версиями почти бесплатно. Если доработок в основной конфигурации всё ещё много — планируйте их постепенный перенос в расширения, начиная с печатных форм и отчётов. Детали конкретной версии всегда сверяйте с описанием поставки и ИТС.

Резервная копия, которую делают «когда вспомнил», — это не резервная копия. Рабочий вариант: база сама выгружается по расписанию в файл `.dt`, старые копии удаляются, а вы хотя бы иногда проверяете, что из копии реально можно восстановиться. Всё это делается из командной строки (bat-файл + планировщик Windows), интерфейс 1С открывать не нужно.

> **Важно.** Главное правило безопасности
> **Восстанавливать можно только в отдельную (пустую) базу, а не поверх рабочей.** Все команды в статье сначала выполняйте на тестовой базе, а на рабочую ставьте уже проверенный скрипт.

## Зачем нужен автоматический бэкап

Данные в 1С можно потерять по-разному: сбой диска, ошибка бухгалтера, неудачное обновление, вирус. Ручная выгрузка спасает только если вы о ней вспомнили вовремя. Автоматический бэкап по расписанию гарантирует, что копия есть всегда — без участия человека.

Наша схема простая:

```
bat-файл  ->  планировщик Windows (ночью)  ->  1cv8 DESIGNER /DumpIB  ->  файл базы.dt
```

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| [1cv8.exe](/glossary/#1cv8) | Исполняемый файл платформы 1С. Ему передаём команду на выгрузку. |
| `DESIGNER` | Режим запуска «Конфигуратор» — из него можно выгружать/загружать базу. |
| [.dt](/glossary/#dt) | Файл выгрузки информационной базы: и структура, и все данные. |
| `/DumpIB` | Ключ «выгрузить информационную базу» в файл `.dt`. |
| bat-файл | Текстовый файл с командами Windows (`backup.bat`). |
| Планировщик заданий | Средство Windows, которое запускает bat по расписанию. |
| `/N`, `/P` | Логин и пароль пользователя 1С, у которого есть права на выгрузку. |
| Ротация | Удаление старых копий, чтобы диск не переполнился. |

## Что понадобится

- Права администратора на компьютере/сервере, где установлена 1С.
- Пользователь 1С с правами **администратора** (для выгрузки и восстановления).
- Свободное место на диске: файл `.dt` по размеру примерно равен объёму базы.
- Место, куда складывать копии: **не тот же диск, где лежит база** (сломался диск с базой — погибнет и копия).

## Шаг 1. Найти 1cv8.exe и узнать путь к базе

Путь к платформе обычно такой: `C:\Program Files\1cv8\8.3.26.0000\bin\1cv8.exe` (номер версии у вас может отличаться). Запомните точный путь.

Путь к базе зависит от её типа:

- **Файловая** база — путь к папке, например `D:\Bases\ERP`. В команде указывается ключом `/F "D:\Bases\ERP"`.
- **Серверная** база — строка подключения вида `Сервер\ИмяБазы`. В команде указывается ключом `/S "srv-1c\ERP"`.

## Шаг 2. Первая выгрузка вручную (проверка)

Прежде чем ставить на расписание, уберите проще всего сделать одну выгрузку руками и убедиться, что всё работает.

```bat
"C:\Program Files\1cv8\8.3.26.0000\bin\1cv8.exe" DESIGNER ^
  /F "D:\Bases\ERP" ^
  /N Администратор ^
  /P пароль ^
  /DumpIB "D:\Backup\erp.dt" ^
  /Out "D:\Backup\backup.log" -NoTruncate ^
  /DisableStartupDialogs
```

| Ключ | Зачем |
| --- | --- |
| `DESIGNER` | Запустить Конфигуратор (а не рабочий режим). |
| `/F "путь"` | Путь к файловой базе. Для серверной вместо этого — `/S "Сервер\ИмяБазы"`. |
| `/N`, `/P` | Пользователь и пароль 1С. Именно в базе, не в Windows. |
| `/DumpIB "файл"` | Собственно выгрузка базы в `.dt`. |
| `/Out "лог" -NoTruncate` | Записать лог, **дописывая** его (не перезатирая историю). |
| `/DisableStartupDialogs` | Не показывать вопросы. Для планового запуска — **обязательно**. |

> **Важно.** Папка для копии должна существовать
> 1С **не создаёт каталоги сама**. Если папки `D:\Backup` (или той, куда пишете `.dt` и лог) нет, выгрузка не выполнится, а в консоли появится «Системе не удаётся найти указанный путь». Создайте папку заранее.

> **Проверка.**
> После команды рядом должен появиться файл `.dt`, а в логе не должно быть слова «Ошибка». Если файл не создался — читайте лог.

Полный список ключей всегда можно посмотреть командой `1cv8.exe HELP DESIGNER`.

## Шаг 3. Собрать bat-файл с датой и ротацией

Чтобы копии не перезатирали друг друга и старые не копились вечно, добавляем дату в имя файла и удаление копий старше 14 дней.

```bat
@echo off
setlocal

set BASE=D:\Bases\ERP
set BAKDIR=D:\Backup
set DT=%DATE:~6,4%-%DATE:~3,2%-%DATE:~0,2%

"C:\Program Files\1cv8\8.3.26.0000\bin\1cv8.exe" DESIGNER ^
  /F "%BASE%" /N Администратор /P пароль ^
  /DumpIB "%BAKDIR%\erp_%DT%.dt" ^
  /Out "%BAKDIR%\backup.log" -NoTruncate ^
  /DisableStartupDialogs

if not exist "%BAKDIR%\erp_%DT%.dt" (
  echo %DATE% %TIME% BACKUP FAILED >> "%BAKDIR%\backup.log"
  exit /b 1
)

:: удалять бэкапы старше 14 дней
forfiles /p "%BAKDIR%" /m erp_*.dt /d -14 /c "cmd /c del @path"
```

Что тут важно:

- `set BASE` и `set BAKDIR` — замените на свои пути.
- `set DT=...` — получает сегодняшнюю дату из системной переменной `%DATE%`.
- Проверка `if not exist ...` — если файл не создался, в лог пишется `BACKUP FAILED`. Так вы заметите сбой, а не узнаете о нём через год.
- `forfiles ... /d -14` — удаляет `.dt` старше 14 дней.

> **Важно.** Осторожно с %DATE%
> Формат `%DATE%` зависит от локали Windows. Конструкция `%DATE:~6,4%` верна только для формата `дд.мм.гггг`. Безопаснее получать дату так:
> ```bat
> for /f %%i in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd"') do set DT=%%i
> ```

## Шаг 4. Поставить на расписание

Создать ежедневное задание на 02:00 от имени системной учётной записи:

```bat
schtasks /create /tn "1C backup ERP" /tr "D:\Scripts\backup-erp.bat" /sc daily /st 02:00 /ru SYSTEM
```

Нюансы:

- Задание от `SYSTEM` работает без входа пользователя в систему — это удобно для сервера.
- Для **серверной** базы учётка в `/N` и `/P` должна существовать **в 1С**, а не в Windows: планировщик её не спрашивает, логин передаётся прямо в строке команды.
- Проверить задание можно в планировщике: там видно историю запусков и код результата.

> **Проверка.**
> Запустите задание вручную из планировщика (правый клик → «Выполнить») и убедитесь, что появился новый `.dt` и свежая запись в `backup.log`.

## Про пароль и безопасность

В примерах логин и пароль стоят прямо в команде (`/N ... /P ...`). Для быстрой проверки это удобно, но для постоянного бэкапа так делать не стоит — это прямое требование стандарта «Безопасное хранение паролей»: секреты не должны лежать в коде и в информационной базе.

- **Отдельный пользователь.** Заведите в 1С отдельного пользователя только для бэкапа, с минимально нужными правами (на выгрузку и восстановление). Не используйте учётку реального сотрудника.
- **Ограничьте доступ к bat-файлу.** Права на него — только у администратора и у учётной записи, под которой работает задание.
- **Безопасное хранилище.** Если есть возможность — храните пароль не строкой в скрипте, а в штатном безопасном хранилище платформы.

## Шаг 5. Проверить, что бэкап рабочий

Бэкап, который ни разу не восстанавливали, — это лотерея. Возьмите свежий `.dt` и восстановите его в **отдельную пустую** базу (см. Шаг 6). Убедитесь, что база открывается и данные на месте. Делайте такую проверку хотя бы раз в месяц.

## Шаг 6. Восстановление (только в пустую базу!)

Восстановление выполняется так же из командной строки:

```bat
"C:\Program Files\1cv8\8.3.26.0000\bin\1cv8.exe" DESIGNER ^
  /F "D:\Bases\ERP_Restore" ^
  /N Администратор ^
  /P пароль ^
  /RestoreIB "D:\Backup\erp_2026-09-09.dt" ^
  /DisableStartupDialogs
```

На мощном сервере загрузку можно ускорить ключом `-JobsCount`: например, `/RestoreIB "D:\Backup\erp_2026-09-09.dt" -JobsCount 4` (по умолчанию — по числу процессоров).

> **Важно.** Никогда не восстанавливайте поверх рабочей базы
> Восстановление затирает базу целиком. Делайте это только в **пустую** базу, созданную специально для проверки или аварийного развёртывания. Для рабочей базы порядок такой: сначала снова сделайте свежий бэкап текущей, затем восстанавливайтесь — и только осознанно.

## Что ещё стоит бэкапить

- **Только конфигурацию** (без данных): ключ `/DumpCfg "файл.cf"`. Файл маленький, его удобно хранить в системе контроля версий.
- **Серверную СУБД** (PostgreSQL, MS SQL): для тяжёлых баз основной бэкап делают средствами СУБД (`pg_dump` и т.п.), а `.dt` — эпизодически, как полный «слепок».
- **Файлы файловой базы** (`.1cd`): копировать можно **только при остановленной базе**, иначе копия будет битой. Обычно проще выгружать `.dt`.

## Проверка и исправление файловой базы

Если файловая база подозрительна, её можно проверить утилитой `chdbfl.exe`:

```bat
chdbfl.exe "D:\Bases\ERP\1Cv8.1CD" 1
```

- `1` — проверять и исправлять (создаётся резервная копия файла базы);
- `0` — только проверять, без изменений.

> **Важно.** База должна быть закрыта
> Перед проверкой убедитесь, что с базой никто не работает. При исправлении (`1`) сначала появится резервная копия — не удаляйте её, пока не убедитесь, что база открывается.

Современный командный аналог «Тестирования и исправления» — ключ `/IBCheckAndRepair`:

```bat
"C:\Program Files\1cv8\8.3.26.0000\bin\1cv8.exe" DESIGNER ^
  /F "D:\Bases\ERP" /N Администратор /P пароль ^
  /IBCheckAndRepair -TestOnly ^
  /Out "D:\Backup\check.log" -NoTruncate /DisableStartupDialogs
```

- `-TestOnly` — только проверить, ничего не менять;
- без `-TestOnly` можно добавить `-ReIndex`, `-LogAndRefsIntegrity`, `-RecalcTotals` и другие (полный список — в справке).

То же самое доступно в Конфигураторе: **Администрирование → Тестирование и исправление**. Наборы ключей командной строки могут отличаться между версиями платформы — сверяйтесь со справкой `1cv8.exe HELP` и документацией ИТС.

## Типовые грабли

> **Важно.** Частые ошибки
> - **Бэкап не делается по расписанию.** Причины: спецсимволы в пароле `/P`, не та учётная запись планировщика, неверный путь к `1cv8.exe`.
> - **Пароль открытым текстом в bat-файле.** Хранить секреты в коде небезопасно (стандарт «Безопасное хранение паролей»). Заведите отдельного пользователя с минимальными правами, ограничьте доступ к bat-файлу и по возможности используйте безопасное хранилище.
> - **«Установка приоритета процесса не выполнена».** Это безвредное предупреждение, бэкап не ломает.
> - **Копии растут бесконечно.** Без ротации диск переполнится — держите 14–30 дней и выносите копии на отдельный диск/в облако.
> - **Восстановили поверх рабочей базы.** Самая опасная ошибка — восстанавливайте только в пустую базу.
> - **Копии лежат на том же диске, что и база.** Умер диск — умерли и база, и бэкап.
> - **Бэкап никогда не проверяли.** Обязательно восстанавливайте `.dt` в тестовую базу хотя бы раз в месяц.

## Куда развивать

- Выносить копии на отдельный диск или в сетевое/облачное хранилище.
- Для серверных баз — подключить штатные средства резервного копирования СУБД (PostgreSQL, MS SQL).
- Хранить выгрузку конфигурации (`.cf`) в системе контроля версий.
- Обновление типовой конфигурации после бэкапа — см. «Обновление типовой конфигурации с доработками».

Инструкция рассчитана на то, что вы делаете это впервые: каждый шаг заканчивается проверкой «что должно получиться». Платформа: **Windows, Apache 2.4, 64-битная 1С**. Для Linux — короткая версия в конце.

**[Apache](/glossary/#apache)** — это веб-сервер: программа, которая принимает запросы из браузера или от внешних систем и передаёт их платформе 1С. Без него база снаружи недоступна.

Что будет в итоге: база 1С доступна через браузер по адресу `http://localhost/erp/`, а HTTP-сервисы и [OData](/glossary/#odata) — через `http://localhost/erp/hs/...` и `/odata/standard.odata`.

## Шаг 1. Проверьте разрядность платформы 1С

[Публикация](/glossary/#publikatsiya) требует, чтобы **разрядность платформы 1С и Apache совпадали**. Посмотрите в `Панель управления → Программы и компоненты`: если 1С установлен как «x64» или в пути `C:\Program Files\1cv8\...` (а не `Program Files (x86)`) — платформа 64-битная, это нам и нужно.

Если стоит только 32-битная платформа — скачайте и установите 64-битную (с сайта releases.1c.ru, раздел «Технологическая платформа», вариант x64). Ставить можно рядом, ничего не сломает.

> **Проверка.** Шаг выполнен, если: есть 64-битная платформа, например в `C:\Program Files\1cv8\8.3.26.0000\bin\` лежит `1cv8.exe`.

## Шаг 2. Скачайте и распакуйте Apache

1. Зайдите на https://www.apachelounge.com/download/ и скачайте **Apache 2.4.x Win64** (zip).
2. Распакуйте архив. Внутри — папка `Apache24`. Скопируйте её в корень диска: должно получиться `C:\Apache24`.

Если при распаковке/запуске позже появится ошибка про `VCRUNTIME140.dll` — установите Microsoft Visual C++ Redistributable x64 (ищите «vc_redist.x64» на сайте Microsoft) и продолжайте.

> **Проверка.** Шаг выполнен, если: существует `C:\Apache24\bin\httpd.exe`.

## Шаг 3. Проверьте, что порт 80 свободен

Откройте командную строку **от имени администратора**:

```bat
netstat -ano | findstr :80 | findstr LISTENING
```

- Ничего не вывелось — порт свободен, идём дальше.
- Вывелась строка с номером процесса (последняя колонка, PID) — порт занят. Узнайте, кто это: `tasklist /fi "PID eq 1234"`. Чаще всего это IIS или Skype. Остановите эту программу или смените порт Apache (в шаге 4 поправьте `Listen 80` на, например, `Listen 8080` — тогда все адреса дальше будут с портом: `http://localhost:8080/erp/`).

## Шаг 4. Установите Apache как службу и запустите

В командной строке от администратора:

```bat
C:\Apache24\bin\httpd.exe -k install
C:\Apache24\bin\httpd.exe -k start
```

Откройте в браузере `http://localhost/` — должна появиться страница **«It works!»** (или страница Apache).

> **Проверка.** Шаг выполнен, если: «It works!» открывается.
>
> Если служба не стартует (`-k start` ругается) — почти всегда причина в конфиге. Выполните `C:\Apache24\bin\httpd.exe -t` — она покажет файл и строку ошибки. И смотрите лог `C:\Apache24\logs\error.log`.

Полезные команды управления службой (понадобятся дальше):

| Команда | Действие |
|---|---|
| `httpd -k start` / `-k stop` / `-k restart` | запустить / остановить / перезапустить |
| `httpd -t` | проверить конфиг на ошибки |
| `services.msc` | служба называется «Apache2.4» — там же автозапуск |

## Шаг 5. Создайте каталог публикации

Создайте папку, например `C:\Publish\erp`. В ней будет лежать файл-описание публикации (`default.vrd`), который создаст Конфигуратор на следующем шаге.

> **Проверка.** Шаг выполнен, если: папка `C:\Publish\erp` существует (пустая).

## Шаг 6. Опубликуйте базу через Конфигуратор

1. Запустите Конфигуратор вашей базы.
2. Меню **Администрирование → Публикация на веб-сервере…**
3. Заполните:
   - **Имя**: `erp` (это часть URL после слэша).
   - **Веб-сервер**: `Apache 2.4`.
   - **Каталог**: `C:\Publish\erp\`.
4. Галочки: **«Публиковать HTTP-сервисы»** — включите, если пользуетесь HTTP-сервисами (MCP, Telegram и т.п., адреса `hs/...`); **«Публиковать веб-сервисы»** — только если у вас есть [веб-сервисы](/glossary/#web-servis) ([SOAP](/glossary/#soap), адреса `ws/...`, это другое); **«Публиковать стандартный интерфейс OData»** — только если он вам нужен; **«Аутентификация по HTTP» / [Basic](/glossary/#basic-auth)** — включите, если доступ будет из внешних программ.
5. Нажмите **«Опубликовать»**. Конфигуратор сам создаст `default.vrd`, сам допишет модуль 1С в `C:\Apache24\conf\httpd.conf` и сам предложит перезапустить сервер — соглашайтесь.

> **Проверка.** Шаг выполнен, если: Конфигуратор не выдал ошибок, а в `C:\Publish\erp` появился файл `default.vrd`, и в `httpd.conf` появилась строка `LoadModule _1cws_module "C:\Program Files\1cv8\...bin\wsap24.dll"`.
>
> Если Конфигуратор ругается, что не нашёл Apache — укажите путь к конфигу вручную (поле «httpd.conf» в этом же окне): `C:\Apache24\conf\httpd.conf`.

## Шаг 7. Откройте базу в браузере

Перейдите на `http://localhost/erp/`.

> **Проверка.** Шаг выполнен, если: открылось окно входа (или сразу интерфейс) 1С:Предприятия. Введите пользователя и пароль ИБ — вы внутри базы через браузер.
>
> Если что-то не так — не мучайтесь наугад, перейдите к разделу «Ошибки и решения» ниже. Там разобраны все типовые случаи.

## Шаг 8. Проверьте HTTP-сервисы (если публикуете для интеграций)

Подставьте свои имя публикации и адрес сервиса (из шпаргалок про MCP/Telegram — шаблон URL вашего сервиса):

```bash
curl -u пользователь:пароль http://localhost/erp/hs/mcp/execute ^
  -H "Content-Type: application/json" ^
  -d "{\"operation\":\"query\",\"query\":\"ВЫБРАТЬ ПЕРВЫЕ 1 Наименование ИЗ Справочник.Номенклатура\"}"
```

> **Проверка.** Шаг выполнен, если: пришёл JSON-ответ (или хотя бы осмысленный HTTP-код), а не «404 Not Found».

## Шаг 9. Автозапуск (если не сделан при установке)

`services.msc` → служба **Apache2.4** → Свойства → Тип запуска: **Автоматически**. Теперь веб-сервер поднимается сам после перезагрузки.

## Ошибки и решения (по шагам, сверху — самые частые)

**Браузер: «Не удаляется доступ к сайту» / connection refused**
Apache не запущен. `C:\Apache24\bin\httpd.exe -k start`, если ошибка — `httpd -t` покажет, где ошибка в конфиге. Проверьте также порт (шаг 3).

**403 Forbidden**
Apache нашёл публикацию, но ему запретили. Откройте `C:\Apache24\conf\httpd.conf`, найдите блок `<Directory "C:/Publish/erp">` — в нём должна быть строка `Require all granted` (это синтаксис Apache 2.4; старые `Order allow,deny / Allow from all` из 2.2 не работают). После правки — `httpd -k restart`.

**401 Unauthorized**
Аутентификация включена, но не пускает: пользователь ИБ с кириллицей в имени (заведите латиницей) или пароль со спецсимволами. Также проверьте, что в публикации включён Basic.

**404 Not Found на /erp/**
Публикация не подключилась: проверьте, что `default.vrd` лежит в каталоге публикации, в `httpd.conf` есть `Alias "/erp" ...` и `SetHandler 1c-application`, и что Apache перезапущен после изменений.

**500 Internal Server Error**
Ошибка на стороне 1С. Смотрите `C:\Apache24\logs\error.log` — там будет текст ошибки платформы (часто: недоступна файловая база по пути из `ib` или неверное имя сервера/базы для серверной).

**«Не найден модуль wsap24.dll» при старте**
Разрядность не совпала: Apache x64 требует 64-битную платформу (шаг 1). Также проверьте, что в `httpd.conf` строка `LoadModule _1cws_module` встречается **один раз** (несколько версий платформы на одном сервере — частая причина; подключайте модуль самой новой версии).

**Всё работало, после перезагрузки сервера — нет**
Служба Apache не в автозапуске — шаг 9. Или платформа 1С обновилась и путь к `wsap24.dll` в `httpd.conf` изменился — поправьте строку `LoadModule`.

## Публикация вручную (когда нужно понимать, что делает Конфигуратор)

`default.vrd` — обычный XML-файл, его можно править блокнотом. Ключевое:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system"
       base="/erp"
       ib="Srvr=&quot;srv1c&quot;;Ref=&quot;erp_prod&quot;;">
    <ws enable="true"/>
    <standardOdata enable="true" reuseSessions="autouse" sessionMaxAge="20"/>
</point>
```

- `base` — имя публикации (часть URL), `ib` — строка подключения: файловая `File=&quot;D:\Bases\ERP&quot;;` или серверная `Srvr=...;Ref=...`.
- `ws` / `standardOdata` / `httpServices` — какие интерфейсы открыты наружу. Не включайте лишнее: каждый открытый интерфейс — потенциальная дверь.

Модуль 1С в `httpd.conf`:

```apache
LoadModule _1cws_module "C:/Program Files/1cv8/8.3.26.0000/bin/wsap24.dll"

Alias "/erp" "C:/Publish/erp/"
<Directory "C:/Publish/erp/">
    Options None
    Require all granted
    SetHandler 1c-application
    ManagedApplicationDescriptor "C:/Publish/erp/default.vrd"
</Directory>
```

После правок — `httpd -k restart`.

## Linux (коротко)

```bash
sudo apt install apache2              # Ubuntu/Debian (yum install httpd — RHEL/CentOS)
```

Конфиги: `/etc/apache2/` (основной `apache2.conf`, логи `/var/log/apache2/`). Дальше те же шаги 5–8: каталог публикации, Конфигуратор (или вручную vrd), проверки теми же URL. Отличия: рестарт `sudo systemctl restart apache2`, а для HTTPS модуля 1С нужны корневые сертификаты (`sudo apt install ca-certificates`) — без них исходящие HTTPS-запросы из 1С падают.

## Безопасность — в конце, но не в последнюю очередь

- Публикуйте только нужные интерфейсы: каждая галочка в публикации — открытая дверь.
- Для доступа извне — HTTPS обязательно (Basic-пароль ходит в каждом запросе), отдельный пользователь ИБ с минимальными правами.
- Первая точка диагностики любой проблемы — `C:\Apache24\logs\error.log`: код ответа и причина почти всегда там.

Если вы никогда не настраивали обмен с маркетплейсами — начните с первых двух разделов: там объясняется, что вообще происходит. Дальше — по шагам, с кодом и проверкой на каждом этапе.

## Что такое «обмен с маркетплейсом» и зачем он нужен

**Маркетплейс** — это торговая площадка (Ozon, Wildberries, Яндекс Маркет), где продавец выставляет товары, а покупатели оформляют заказы. Сама площадка — не ваш склад: заказы лежат у неё, а учёт (остатки, цены, документы) ведётся в 1С.

Руками это выглядит так: зашли в личный кабинет, скачали список заказов, перенесли в 1С, потом вручную поправили остатки. Работает — пока заказов десять. При потоке это превращается в рутину и ошибки.

**Обмен** — это когда 1С сама, по расписанию, без человека:

- **забирает** из маркетплейса новые заказы (направление «pull» — «тянем к себе»);
- **отдаёт** маркетплейсу актуальные остатки и цены (направление «push» — «толкаем от себя»).

Связь идёт через **[API](/glossary/#api)** — программный интерфейс, по которому одна система обращается к другой. Никаких «кнопок» — только запросы и ответы.

## Словарик новичка

Пять минут на эти слова сэкономят часы непонимания дальше.

| Слово | Что значит простыми словами |
|---|---|
| **API** | Набор «дверей», в которые можно постучать из программы, чтобы что-то узнать или сделать |
| **[Эндпоинт](/glossary/#endpoint)** | Конкретный адрес этой двери, например `/v3/posting/fbs/list` |
| **[Ключ / токен](/glossary/#token)** | Пароль для программы. Площадка выдаёт его в личном кабинете |
| **Запрос / ответ** | Вы отправляете данные (запрос) — площадка возвращает результат (ответ) |
| **[JSON](/glossary/#json)** | Текстовый формат, в котором данные передаются туда и обратно. Похож на структуру: `{"имя": "значение"}` |
| **FBS / FBO / DBS** | Схемы работы: FBS — товар лежит у вас, FBO — на складе площадки, DBS — вы везёте сами. Для обмена важны: у FBS и FBO разные эндпоинты заказов |
| **Отправление** | Один заказ (или посылка) на площадке. У него есть свой номер и состав |
| **Артикул / SKU** | Идентификатор товара на площадке. Ваш артикул в 1С и SKU площадки нужно связать между собой |
| **Остаток** | Сколько товара доступно к продаже |
| **Pull / Push** | Pull — забираем данные к себе, push — отправляем свои наружу |
| **Лимит (rate limit)** | Ограничение «не больше N запросов в минуту», иначе площадка отвечает `429` |

## Как это работает

```
        заказы (pull, 1С ← площадка)   ←───────────────
  1С                                                   Маркетплейс
        остатки и цены (push, 1С → площадка)  ────────→
```

Периодически (по расписанию) 1С выполняет два задания:

1. «Забрать новые заказы» — обращается к API площадки, получает список отправлений, создаёт по ним документы.
2. «Отправить остатки и цены» — берёт изменённые товары из 1С и отправляет их на площадку.

Всё это — обычные HTTP-запросы, то же `HTTPСоединение`, что и в шпаргалке про [HTTP-API](/cheats/http-api-1c/). Отличаются только адреса и способ авторизации у каждой площадки.

## Что понадобится

- Платформа 1С 8.3 и сервер (или регламентное задание) с **доступом в интернет** — именно с сервера 1С пойдут запросы;
- аккаунт продавца на площадке и права выдать **API-ключи**;
- базовое понимание HTTP-запросов (см. шпаргалку [«HTTP-запросы к внешним API из 1С»](/cheats/http-api-1c/)).

## Шаг 1. Получаем ключи доступа

Ключи — это «пропуск» для программы. Выдаются в личном кабинете продавца и **действуют от имени вашего аккаунта**, поэтому обращаться с ними нужно как с паролем.

| Площадка | Где взять ключ |
|---|---|
| **Ozon** | Личный кабинет → Настройки → API-ключи. Нужны сразу два значения: **Client-Id** и **Api-Key** |
| **Wildberries** | Личный кабинет → Настройки → Доступ к API. Выдаётся **токен** (одна строка) |
| **Яндекс Маркет** | Личный кабинет → Настройки → API. Выдаётся **OAuth-токен** |

> **Важно.** Ключ нельзя вставлять в код или в коммитить в git. Храните его в безопасном хранилище (`ЗащищенноеХранилищеДанных`) или в константе с ограниченными правами — подробнее в шпаргалке про [HTTP-API](/cheats/http-api-1c/).

## Шаг 2. Сравнение API трёх площадок

Схема одна, но адреса и авторизация разные. Эта таблица — ваш «маячок» при чтении документации.

| | Ozon Seller API | Wildberries | Яндекс Маркет |
|---|---|---|---|
| **Базовый адрес** | `api-seller.ozon.ru` | `marketplace-api.wildberries.ru` | `api.partner.market.yandex.ru` |
| **Авторизация** | заголовки `Client-Id` + `Api-Key` | заголовок `Authorization: Bearer <токен>` | заголовок `Authorization: Bearer <OAuth-токен>` |
| **Забрать заказы** | `POST /v3/posting/fbs/list` | `GET /api/v3/orders/new` | `POST /campaigns/{id}/orders` |
| **Отправить остатки** | `POST /v1/product/import/stocks` | `PUT /api/v3/stocks/{склад}` | `PUT /businesses/{id}/offer-mappings` |

> **Обязательно сверяйтесь с официальной документацией площадки.** Версии API меняются часто (был `v2` — стал `v3`, старые адреса отключают). Считайте примеры ниже шаблоном, а точные имена полей берите из актуальной документации.

## Шаг 3. Первый запрос из 1С

Напишем одну универсальную функцию, чтобы не дублировать код для каждой площадки. Она умеет GET, POST, PUT, PATCH и DELETE и сама разбирает JSON-ответ.

```bsl
// Универсальный вызов REST API маркетплейса.
// Хост        — например "api-seller.ozon.ru"
// Путь        — например "/v3/posting/fbs/list"
// Метод       — "GET", "POST", "PUT", "PATCH", "DELETE"
// ТелоСтрокой — JSON-строка тела запроса (для GET можно пустую)
// Заголовки   — структура с дополнительными заголовками (ключи, авторизация)
Функция ВызватьAPI(Хост, Путь, Метод, ТелоСтрокой, Заголовки) Экспорт

    Соединение = Новый HTTPСоединение(Хост, 443, , , , 30,
        Новый ЗащищенноеСоединениеOpenSSL);

    Запрос = Новый HTTPЗапрос(Путь);
    Запрос.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");
    Для Каждого Заголовок Из Заголовки Цикл
        Запрос.Заголовки.Вставить(Заголовок.Ключ, Заголовок.Значение);
    КонецЦикла;

    Если НЕ ПустаяСтрока(ТелоСтрокой) Тогда
        Запрос.УстановитьТелоИзСтроки(ТелоСтрокой, КодировкаТекста.UTF8);
    КонецЕсли;

    Если Метод = "GET" Тогда
        Ответ = Соединение.Получить(Запрос);
    ИначеЕсли Метод = "POST" Тогда
        Ответ = Соединение.ОтправитьДляОбработки(Запрос);
    ИначеЕсли Метод = "PUT" Тогда
        Ответ = Соединение.Записать(Запрос);
    ИначеЕсли Метод = "PATCH" Тогда
        Ответ = Соединение.Изменить(Запрос);
    ИначеЕсли Метод = "DELETE" Тогда
        Ответ = Соединение.Удалить(Запрос);
    Иначе
        Ответ = Соединение.ВызватьHTTPМетод(Метод, Запрос);
    КонецЕсли;

    Если Ответ.КодСостояния <> 200 Тогда
        ВызватьИсключение "HTTP " + Ответ.КодСостояния + ": "
            + Ответ.ПолучитьТелоКакСтроку();
    КонецЕсли;

    Чтение = Новый ЧтениеJSON;
    Чтение.УстановитьСтроку(Ответ.ПолучитьТелоКакСтроку());
    Результат = ПрочитатьJSON(Чтение, Ложь);
    Чтение.Закрыть();

    Возврат Результат;

КонецФункции
```

Чтобы не собирать JSON руками (легко ошибиться в кавычках), сделаем маленький помощник:

```bsl
// Превращает структуру или массив 1С в JSON-строку
Функция СобратьJSON(Данные) Экспорт

    Запись = Новый ЗаписьJSON;
    Запись.УстановитьСтроку(Новый НастройкиСериализацииJSON);
    ЗаписатьJSON(Запись, Данные);
    Возврат Запись.Закрыть();

КонецФункции
```

> **Важно.** Запросы выполняются **на сервере** (в регламентном задании). На клиенте объект `HTTPСоединение` недоступен.

## Шаг 4. Забираем новые заказы (pull)

### Ozon — пример подробно

Ключи кладём в заголовки, тело запроса собираем структурой:

```bsl
Заголовки = Новый Структура;
Заголовки.Вставить("Client-Id", КлючClientIdOzon());
Заголовки.Вставить("Api-Key",   КлючApiOzon());

// Фильтр: заказы начиная с определённого момента, страница по 50
Фильтр = Новый Структура;
Фильтр.Вставить("dir", "ASC");
Фильтр.Вставить("filter", Новый Структура("since",
    Формат(НачалоДня(ТекущаяДатаСеанса()), "ДФ=yyyy-MM-dd'T'HH:mm:ss'Z'")));
Фильтр.Вставить("limit",  50);
Фильтр.Вставить("offset", 0);

Ответ = ВызватьAPI("api-seller.ozon.ru", "/v3/posting/fbs/list",
    "POST", СобратьJSON(Фильтр), Заголовки);

// Ответ.result.postings — массив отправлений
Для Каждого Отправление Из Ответ.result.postings Цикл
    СоздатьДокументПоЗаказу(Отправление);
КонецЦикла;
```

Если отправлений больше 50, площадка отдаёт их постранично: увеличивайте `offset` на `limit` и повторяйте, пока ответ не станет пустым. У разных площадок вместо `offset` бывает **курсор** — «закладка», которую нужно передать в следующий запрос.

### Wildberries и Яндекс Маркет — коротко

```bsl
// Wildberries: новые заказы
Заголовки = Новый Структура("Authorization", "Bearer " + ТокенWB());
Ответ = ВызватьAPI("marketplace-api.wildberries.ru", "/api/v3/orders/new",
    "GET", "", Заголовки);

// Яндекс Маркет: заказы кампании
Заголовки = Новый Структура("Authorization", "Bearer " + ТокенМаркета());
Ответ = ВызватьAPI("api.partner.market.yandex.ru",
    "/campaigns/" + ИдентификаторКампании + "/orders", "GET", "", Заголовки);
```

> **Не создавайте дубли.** Регламентное задание запускается регулярно и может увидеть один и тот же заказ повторно. Перед созданием документа проверяйте, не заведён ли уже такой номер отправления (храните его в регистре), а в теле создаваемого документа сохраняйте номер площадки. Это называется **[идемпотентность](/glossary/#idempotentnost)** — «повторный запуск не должен плодить копии».

## Шаг 5. Отправляем остатки и цены (push)

Отправляем только то, что изменилось, и **пачками** — площадки принимают не более N товаров за один запрос (обычно 100–1000, уточняйте в документации).

### Ozon

```bsl
Стоки = Новый Массив;
Позиция = Новый Структура("sku", КодТовараOzon);
Позиция.Вставить("stock", ДоступныйОстаток(Товар));
Стоки.Добавить(Позиция);

Тело = СобратьJSON(Новый Структура("stocks", Стоки));
ВызватьAPI("api-seller.ozon.ru", "/v1/product/import/stocks",
    "POST", Тело, Заголовки);
```

### Wildberries и Яндекс Маркет

```bsl
// Wildberries: остатки по складу (метод PUT)
Тело = СобратьJSON(Новый Структура("stocks", Стоки));
ВызватьAPI("marketplace-api.wildberries.ru",
    "/api/v3/stocks/" + ИдентификаторСклада, "PUT", Тело, Заголовки);

// Яндекс Маркет: остатки и цены одной картой товара
Тело = СобратьJSON(СписокПредложений);
ВызватьAPI("api.partner.market.yandex.ru",
    "/businesses/" + ИдентификаторБизнеса + "/offer-mappings", "PUT", Тело, Заголовки);
```

## Шаг 6. Ставим на расписание

Обмен — это не разовое действие, а фоновые задания. В 1С это **[регламентные задания](/glossary/#reglamentnoe-zadanie)** (Администрирование → Регламентные задания), которые вызывают ваши процедуры с нужной периодичностью.

| Что делаем | Разумная частота | Почему так |
|---|---|---|
| Забираем заказы | каждые 5–15 минут | Заказ должен быстро попасть в учёт |
| Отправляем остатки и цены | по изменениям или раз в 10–30 минут | Чаще — упрётесь в лимиты площадки |

> **Почему не «сразу при проведении документа».** Если в момент продажи внешняя площадка недоступна, операция у пользователя упадёт. Надёжнее записать задачу в очередь и отправить её отдельным заданием с повторами — этому целиком посвящена шпаргалка [«Исходящая очередь»](/cheats/outgoing-queue-1c/).

## Ошибки и лимиты

- **`401` / `403`** — неверный или просроченный ключ, либо ключ выдан для другого API (у Wildberries разные токены для заказов, статистики и контента).
- **`429`** — превышен лимит запросов. Площадка обычно присылает заголовок `Retry-After` с числом секунд — подождите столько и повторите, а не «долбите» сразу.
- **`400`** — ошибка в данных запроса: площадка присылает JSON с описанием, прочитайте его (часто это неизвестный `sku` или неверный формат даты).
- **`5xx`** — проблема на стороне площадки; повторите запрос позже.

Всегда проверяйте код ответа и **повторяйте с ограничением** (например, не более 5–10 раз) — иначе «мёртвый» запрос будет крутиться вечно.

## Типовые грабли

- **Версии API меняются.** Эндпоинты `v2` постепенно заменяются на `v3` и отключаются. Если обмен «вдруг перестал работать» — первым делом проверьте, не устарел ли адрес.
- **Даты и часовые пояса.** В API даты обычно в формате ISO (`2026-09-10T12:00:00Z`, время UTC). Сравнивайте с учётом пояса, иначе «пропустите» или задвоите заказы.
- **Кодировка.** Тело шлите в UTF-8 явно (`КодировкаТекста.UTF8`) — иначе кириллица в названиях поедет.
- **Разные схемы работы.** FBS, FBO и DBS используют разные эндпоинты и разные сценарии. Не смешивайте их в одном задании.
- **Связка товаров.** Ваш артикул в 1С и SKU площадки — разные вещи. Держите таблицу соответствия, иначе остатки уйдут «не тому» товару.
- **TLS на Linux.** Серверу 1С под Linux нужны корневые сертификаты (`ca-certificates`), иначе HTTPS не поднимется (см. шпаргалку про [HTTP-API](/cheats/http-api-1c/)).
- **Ключи в git.** Токен в открытом виде в коде — это доступ к вашему магазину для любого, кто увидит репозиторий.

## Куда развивать

Когда базовый обмен заработал, естественные следующие шаги:

- **Загрузка карточек товаров** — создание и обновление описаний, фото, габаритов.
- **Ответы на отзывы и вопросы** — те же API, отдельные эндпоинты.
- **Печать этикеток FBS** — площадки отдают готовый PDF/стикер по отправлению.
- **Автоматические акции и промо** — управление ценами по расписанию площадки.

Логика не меняется: новое действие — это новый эндпоинт в вашей функции `ВызватьAPI` и новая процедура, вызывающая её.

Если вы никогда не делали HTTP-сервис в 1С — начните с первых двух разделов: там объясняется, что это вообще такое. Дальше — по шагам, с кодом и проверкой на каждом этапе. Никакого опыта веб-разработки не требуется.

## Что такое HTTP-сервис и когда он нужен

До этого во всех примерах связь с внешним миром шла «наружу»: 1С сама отправляла запрос во внешний API (см. [«HTTP-запросы к внешним API из 1С»](/cheats/http-api-1c/)). Здесь всё наоборот — **запрос приходит в 1С**:

```
Внешняя система (сайт, сервис, приложение)
        │  HTTP-запрос
        ▼
   HTTP-сервис 1С  →  ваш код на BSL  →  база 1С
        │  HTTP-ответ (JSON)
        ▲
```

**HTTP-сервис** — это «приёмная» в вашей базе: адрес, по которому внешняя система присылает запрос, и код на BSL, который этот запрос обрабатывает и отвечает. Так работают:

- приём заказов с сайта или из мобильного приложения;
- [вебхуки](/glossary/#webhook) от внешних сервисов (Telegram присылает сообщения — см. [«Telegram-бот на 1С»](/cheats/telegram-bot-1c/));
- приём данных из другой учётной системы (обмен между базами);
- «дверь» для MCP-сервера или ИИ-клиента (см. [«MCP-сервер для 1С»](/cheats/mcp-server-1c/)).

> **Не путайте с OData.** OData (см. [«OData: доступ к данным 1С»](/cheats/odata-1c/)) даёт готовый CRUD по объектам и включается галочкой, но **никакой вашей логики** в нём нет. HTTP-сервис — когда нужен свой контракт и свои правила: «принять заказ, проверить остатки, создать документ, ответить номером».

## Словарик новичка

| Слово | Что значит простыми словами |
|---|---|
| **HTTP-сервис** | Набор адресов в вашей базе, по которым принимаются внешние запросы |
| **Корневой URL** | Общая часть адреса сервиса, например `orders` |
| **Шаблон URL** | Часть адреса **после** корневого URL, например `/{Номер}` (полный путь тогда — `.../hs/orders/A-100`) |
| **Обработчик** | Функция на BSL, которую 1С вызывает, когда пришёл запрос |
| **Метод (GET/POST/PUT/DELETE)** | Что клиент хочет сделать: прочитать / создать / изменить / удалить |
| **Тело запроса** | Данные, которые клиент прислал (обычно JSON) |
| **Код состояния** | Число в ответе: `200` — успех, `400` — ошибка в запросе, `404` — не найдено, `500` — сбой у нас |
| **[Basic-аутентификация](/glossary/#basic-auth)** | Логин и пароль, которые клиент присылает в каждом запросе |
| **[JSON](/glossary/#json)** | Текстовый формат данных: `{"поле": "значение"}` |

## Что понадобится

- Платформа 1С 8.3.5 и выше — HTTP-сервисы появились именно в 8.3.5 (проверьте: **Справка → О программе**);
- база, **опубликованная на веб-сервере** (см. [«Публикация 1С на Apache: пошагово с нуля»](/cheats/apache-publish-1c/)) — без публикации сервис снаружи недоступен;
- отдельный пользователь ИБ с именем **латиницей** (для Basic-аутентификации) и минимальными правами.

## Шаг 1. Создаём HTTP-сервис в Конфигураторе

1. Откройте Конфигуратор, найдите ветку **Общие → HTTP-сервисы**.
2. **Добавить**, задайте:
   - **Имя**: `OrdersAPI`;
   - **Корневой URL**: `orders` (латиницей, без пробелов — это часть адреса).
3. У сервиса раскройте **Шаблоны URL → Добавить**:

| Свойство | Значение |
|---|---|
| Имя | `Заказ` |
| Шаблон | `/{Номер}` |
| Метод | `POST` |
| Обработчик | `ПринятьЗаказPOST` |

Шаблон указывается **без корневого URL** — 1С сама склеит `Корневой URL + Шаблон` (получится адрес `.../hs/orders/{Номер}`). `{Номер}` в фигурных скобках — это **параметр**: вместо него подставится реальное значение из адреса (например, в адресе `.../hs/orders/A-100` параметр `{Номер}` = `A-100`). Такие параметры потом доступны в коде.

> **Проверка.** Шаг выполнен, если в дереве появился HTTP-сервис `OrdersAPI` с корневым URL `orders` и шаблоном `/{Номер}`.

## Шаг 2. Пишем обработчик

Обработчик — это функция в **модуле HTTP-сервиса**. Открыть модуль: в дереве конфигурации щёлкните сервис правой кнопкой → **«Открыть модуль»**. Функция принимает объект `Запрос` и обязана вернуть `HTTPСервисОтвет`.

```bsl
Функция ПринятьЗаказPOST(Запрос)

    Ответ = Новый HTTPСервисОтвет(200);
    Ответ.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");

    Попытка
        // 1. Тело запроса — это JSON, читаем как строку и разбираем
        Тело = Запрос.ПолучитьТелоКакСтроку();
        Чтение = Новый ЧтениеJSON;
        Чтение.УстановитьСтроку(Тело);
        Данные = ПрочитатьJSON(Чтение, Ложь);
        Чтение.Закрыть();

        // 2. Номер из адреса: /orders/{Номер}
        НомерЗаказа = Запрос.ПараметрыURL["Номер"];

        // 3. Наша логика
        Результат = СоздатьЗаказИзJSON(НомерЗаказа, Данные);

        // 4. Формируем JSON-ответ
        Ответ.КодСостояния = 201;
        Ответ.УстановитьТелоИзСтроки(
            СобратьJSON(Новый Структура("номер, статус", НомерЗаказа, "принят")),
            КодировкаТекста.UTF8);

    Исключение
        // 5. Ошибку отдаём клиенту кодом 400 и текстом
        Ответ.КодСостояния = 400;
        Ответ.УстановитьТелоИзСтроки(
            СобратьJSON(Новый Структура("ошибка", ОписаниеОшибки())),
            КодировкаТекста.UTF8);
    КонецПопытки;

    Возврат Ответ;

КонецФункции

Функция СобратьJSON(Данные)
    Запись = Новый ЗаписьJSON;
    Запись.УстановитьСтроку(Новый НастройкиСериализацииJSON);
    ЗаписатьJSON(Запись, Данные);
    Возврат Запись.Закрыть();
КонецФункции
```

> **Важно: `СоздатьЗаказИзJSON` — это ваша логика, а не функция платформы.** Так назван код, который создаёт заказ из уже разобранного JSON. Чтобы пример запускался, вот минимальная заглушка (в рабочем коде здесь заполнение и запись документа):

```bsl
Функция СоздатьЗаказИзJSON(НомерЗаказа, Данные)
    // Данные — структура из JSON; поля достаются, например, так: Данные.Получить("товар").
    // Заглушка: ничего не создаём, просто возвращаем номер.
    Возврат НомерЗаказа;
КонецФункции
```

> **Проверка.** Шаг выполнен, если функция `ПринятьЗаказPOST` существует в модуле сервиса и возвращает `HTTPСервисОтвет`.

## Шаг 3. Откуда брать данные запроса

У объекта `Запрос` есть всё, что прислал клиент:

| Что нужно | Как получить |
|---|---|
| Тело (JSON) строкой | `Запрос.ПолучитьТелоКакСтроку()` |
| Тело как файл/поток (большие данные) | `Запрос.ПолучитьТелоКакДвоичныеДанные()` / `Запрос.ПолучитьТелоКакПоток()` |
| Параметры из шаблона `/{Номер}` | `Запрос.ПараметрыURL["Номер"]` |
| Параметры строки запроса `?код=5&дата=...` | `Запрос.ПараметрыЗапроса["код"]` |
| HTTP-метод (`GET`, `POST`…) | `Запрос.HTTPМетод` |
| Заголовки запроса | `Запрос.Заголовки["Content-Type"]` |

Разница, которую чаще всего путают: **`ПараметрыURL`** — это части самого адреса из шаблона (адрес `.../hs/orders/A-100` → `A-100`), а **`ПараметрыЗапроса`** — это то, что идёт после вопросительного знака (`?limit=10` → `10`).

> **Если клиент прислал список** (в JSON был массив объектов, а не один), `ПрочитатьJSON` вернёт массив структур — обходите его циклом: `Для Каждого Элемент Из Данные Цикл ... КонецЦикла;`.

## Шаг 4. Формируем ответ правильно

Ответ всегда — объект `HTTPСервисОтвет`. Главное в нём:

```bsl
Ответ = Новый HTTPСервисОтвет(200);          // код состояния
Ответ.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");
Ответ.УстановитьТелоИзСтроки(ТелоСтрокой, КодировкаТекста.UTF8);
Возврат Ответ;
```

Какие коды использовать:

| Код | Когда |
|---|---|
| `200 OK` | запрос обработан (например, вернули данные) |
| `201 Created` | создали объект |
| `400 Bad Request` | клиент прислал мусор (не разобрался JSON, нет обязательного поля) |
| `401 Unauthorized` | не прошла аутентификация |
| `404 Not Found` | объекта/адреса нет |
| `500 Internal Server Error` | непредвиденный сбой у нас |

> **Про имена полей JSON.** Ключи вроде `номер` и `статус` — это то, что увидит внешняя система; они произвольны. По договорённости с ней их обычно пишут латиницей (`number`, `status`) — так проще другим разработчикам, но это не требование платформы.

> **Важно про Apache.** Веб-сервер Apache не отдаёт произвольные коды состояния (в отличие от IIS) — держитесь стандартных из таблицы выше. И кодировку тела ответа указывайте явно (`КодировкаТекста.UTF8`), иначе кириллица поедет.

## Шаг 5. Авторизация: закрываем сервис

Открытый наружу сервис без аутентификации — это открытая база. Минимально необходимое:

1. Создайте отдельного пользователя ИБ, **имя латиницей** (например, `api_service`) — с кириллическим именем Basic-аутентификация не сработает.
2. Дайте ему **минимальные роли** (только то, что реально нужно сервису) и запретите интерактивный вход.
3. При публикации базы включите **Basic-аутентификацию** (см. [«Публикация 1С на Apache»](/cheats/apache-publish-1c/)).
4. Работайте по **HTTPS** — пароль в Basic-заголовке передаётся в каждом запросе и без TLS виден в сети.

> **Проверка.** Шаг выполнен, если запрос без логина/пароля получает `401`, а с правильными — обрабатывается.

## Шаг 6. Публикуем и проверяем

1. **Администрирование → Публикация на веб-сервере** → включите галочку **«Публиковать HTTP-сервисы»** → **Опубликовать**.
2. Проверьте снаружи (замените адрес, логин и пароль на свои):

```bash
curl -u api_service:пароль -X POST "http://localhost/erp/hs/orders/A-100" \
  -H "Content-Type: application/json" \
  -d "{\"товар\":\"Стол\",\"количество\":2}"
```

Разбор адреса: `http://localhost/erp/` — публикация базы (`erp` — имя публикации, у вас может быть другое), `hs/` — признак HTTP-сервиса, `orders/` — корневой URL сервиса, `A-100` — значение параметра `{Номер}` из шаблона `/{Номер}`.

> **Про `localhost`.** Это та же машина, где стоит веб-сервер. При проверке с другого компьютера замените `localhost` на IP или домен.

> **Проверка.** Шаг выполнен, если в ответ пришёл JSON `{"номер":"A-100","статус":"принят"}` и код `201`. Если `404` — сервис не опубликован или не совпал корневой URL; если `401` — не прошла аутентификация.

## Собираем вместе: мини REST-сервис

Чтобы был полный пример, добавим к тому же сервису `OrdersAPI` ещё пару методов:

| Шаблон | Метод | Обработчик | Смысл |
|---|---|---|---|
| `/{Номер}` | GET | `ПолучитьЗаказGET` | прочитать заказ |
| `/` | POST | `СоздатьЗаказPOST` | создать новый |

```bsl
Функция ПолучитьЗаказGET(Запрос)

    Номер = Запрос.ПараметрыURL["Номер"];
    Заказ = НайтиЗаказ(Номер);   // ваша функция поиска

    Если Заказ = Неопределено Тогда
        Ответ = Новый HTTPСервисОтвет(404);
        Ответ.УстановитьТелоИзСтроки(
            СобратьJSON(Новый Структура("ошибка", "Заказ не найден")),
            КодировкаТекста.UTF8);
        Возврат Ответ;
    КонецЕсли;

    Ответ = Новый HTTPСервисОтвет(200);
    Ответ.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");
    Ответ.УстановитьТелоИзСтроки(СобратьJSON(Заказ), КодировкаТекста.UTF8);
    Возврат Ответ;

КонецФункции

// Заглушка: в рабочем коде здесь поиск документа заказа по номеру.
Функция НайтиЗаказ(Номер)
    Возврат Неопределено;
КонецФункции
```

Так получается настоящий [REST](/glossary/#rest): адрес `/{Номер}` (элемент коллекции) отвечает по-разному в зависимости от метода — `GET` читает, `PUT` изменяет, `DELETE` удаляет; а `POST` на корневой адрес `/` создаёт новый объект. Метод задаётся в шаблоне URL рядом с обработчиком.

> **Идемпотентность.** Внешняя система может повторить запрос (сеть моргнула, не дождалась ответа). Чтобы не создать два заказа, храните внешний номер заказа и перед созданием проверяйте, не заведён ли он уже. Подробнее — в [«Исходящая очередь: надёжная отправка во внешние системы»](/cheats/outgoing-queue-1c/).

## Типовые грабли

> **Частые ошибки.**
> - **`404 Not Found` на весь сервис.** Не включена галочка «Публиковать HTTP-сервисы», не совпал корневой URL, или после правки конфигурации не опубликовали заново. Проверьте адрес: `hs/<корневойURL>/<путь>`.
> - **`405 Method Not Allowed`.** Метод в запросе не совпал с методом в шаблоне URL (в шаблоне `POST`, а прислали `GET`).
> - **`401` при верных данных.** Имя пользователя кириллицей или Basic не включён в публикации.
> - **Кириллица превратилась в кракозябры.** Тело и ответ не в UTF-8: читайте с `ПолучитьТелоКакСтроку()` и отдавайте с `УстановитьТелоИзСтроки(..., КодировкаТекста.UTF8)`, заголовок `Content-Type: application/json; charset=utf-8`.
> - **Тело пустое.** Для `GET` тело обычно не передаётся — данные идут в шаблоне URL или в параметрах запроса (`?ключ=значение`).
> - **Обработчик «не видит» изменения.** После правки модуля сервиса нужно заново **обновить конфигурацию БД** (F7) и при необходимости перезапустить публикацию.
> - **Не работает на клиенте.** `HTTPСервисЗапрос`, `HTTPСервисОтвет` и сам HTTP-сервис живут **только на сервере** — это серверная сторона, клиентский код их не выполняет.
> - **Открыли лишнее.** Каждый опубликованный сервис — входная дверь. Минимальные права пользователя + HTTPS + белый список операций, а не «выполнить произвольный код».
> - **Долгий обработчик.** Если внешняя система ждёт ответа, а вы делаете тяжёлую работу — она отвалится по таймауту. Быстро отвечайте `200`, а тяжёлое выносите в фоновое задание (см. [«Исходящая очередь»](/cheats/outgoing-queue-1c/) и [«Telegram-бот на 1С»](/cheats/telegram-bot-1c/)).

> **Не отдавайте `ОписаниеОшибки()` наружу в рабочей системе.** Текст внутренней ошибки удобен при отладке, но постороннему он показывает устройство базы. В проде пишите ошибку в журнал регистрации, а клиенту отвечайте общим сообщением (например, «внутренняя ошибка»).

## Куда развивать

- **Аутентификация не только Basic** — токены, подпись запроса, проверка IP.
- **Версионирование API** — добавьте `/v1/...` в шаблон, чтобы менять контракт без ломки старых клиентов.
- **Документирование** — отдайте клиенту примеры запросов и кодов ответов, иначе он будет угадывать.
- **Ограничение частоты** — защита от слишком частых запросов от одного клиента.

1С умеет отправлять письма сама: уведомления клиентам, счета, отчёты руководителю. Чтобы это заработало, нужно знать адрес почтового сервера, порт и логин с паролем — и написать несколько строк кода. Разберём по шагам.

## Что такое SMTP и когда это нужно

**[SMTP](/glossary/#smtp)** — это «язык», на котором программы передают письма на почтовый сервер. Вы отправляете письмо не напрямую получателю, а на сервер своего почтового провайдера (Яндекс, Mail.ru, корпоративный Exchange), а он уже доставляет его дальше.

```
1С  --(SMTP)-->  почтовый сервер  --(интернет)-->  ящик получателя
```

Отправка и приём — разные вещи:

- **SMTP** — отправка писем (то, что нужно нам).
- **[POP3 / IMAP](/glossary/#imap-pop3)** — приём писем (если нужно читать входящие).

Типовые задачи, где это нужно: уведомление о заказе, отправка счёта или акта, ежедневный отчёт по расписанию, письмо при ошибке обмена.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| SMTP | Протокол отправки почты. |
| Почтовый сервер | «Узел» провайдера, через который уходит письмо, например `smtp.yandex.ru`. |
| Порт | Номер «двери» на сервере. Для отправки обычно 465 или 587. |
| **[SSL / TLS](/glossary/#ssl-tls)** | Шифрование канала, чтобы пароль и письмо не шли открытым текстом. |
| Аутентификация | Проверка логина и пароля перед отправкой. |
| Пароль приложения | Отдельный пароль для программ (не от входа в почту). |
| Вложение | Файл внутри письма. |

## Что понадобится

- Платформа 1С 8.3 (подойдёт и 8.2).
- Настройки почтового ящика: **сервер, порт, логин, пароль** (обычно берутся в справке провайдера или у админа).
- У сервера 1С должен быть доступ в интернет.

## Шаг 1. Узнать настройки почтового сервера

Возьмите их на сайте провайдера или у администратора. Частые варианты:

| Провайдер | Сервер | Порт | Шифрование |
| --- | --- | --- | --- |
| Яндекс | `smtp.yandex.ru` | 465 | SSL |
| Mail.ru | `smtp.mail.ru` | 465 | SSL |
| Gmail | `smtp.gmail.com` | 465 | SSL |
| Свой / Exchange | уточните у админа | 587 | STARTTLS |

> **Важно.** Яндекс, Mail.ru и Gmail не пускают программы по обычному паролю от входа — нужно создать **пароль приложения** в настройках безопасности почты. Иначе будет ошибка авторизации `535`.

## Шаг 2. Отправить письмо из кода

Отправка всегда одинаковая: создаём объект **[ИнтернетПочта](/glossary/#internet-pochta)**, заполняем профиль, подключаемся, собираем письмо и отправляем.

```bsl
// 1. Данные почтового сервера
Профиль = Новый ИнтернетПочтовыйПрофиль;
Профиль.АдресСервераSMTP         = "smtp.yandex.ru";
Профиль.ПортSMTP                 = 465;
Профиль.ПользовательSMTP         = "robot@example.ru";
Профиль.ПарольSMTP               = "пароль_приложения";
Профиль.ИспользоватьSSLSMTP      = Истина; // для порта 465
Профиль.Таймаут                  = 30;

// 2. Подключение к почтовой службе
Почта = Новый ИнтернетПочта;
Почта.Подключиться(Профиль);

// 3. Само письмо
Письмо = Новый ИнтернетПочтовоеСообщение;
Письмо.Отправитель = "robot@example.ru";
Письмо.Получатели.Добавить("client@example.ru");
Письмо.Копии.Добавить("boss@example.ru");
Письмо.Тема = "Счёт за день";
Письмо.Кодировка = КодировкаТекста.UTF8;

Текст = Письмо.Тексты.Добавить("Добрый день! Счёт во вложении.");
Текст.ТипТекста = ТипТекстаПочтовогоСообщения.ПростойТекст;

// 4. Отправка
Почта.Послать(Письмо);
Почта.Отключиться();
```

> **Проверка.** Если код прошёл без ошибок — письмо ушло. Не пришло — смотрите папку «Спам» и читайте текст ошибки в 1С.

Разберём по строкам:

- `ИнтернетПочтовыйПрофиль` — «анкета» сервера: адрес, порт, логин, пароль.
- `Почта.Подключиться(Профиль)` — соединение с почтовой службой. Второй параметр — протокол **приёма** (POP3 по умолчанию), на отправку он не влияет.
- `Письмо.Получатели.Добавить(...)` — добавить адрес; так же работают `Копии` и `СлепыеКопии`.
- `Почта.Послать(Письмо)` — собственно отправка. Метод возвращает соответствие ошибочных адресов: если адрес не принят, он там будет.

## Шаг 3. Вложить файл

Вложение добавляется одной строкой — по пути к файлу или из двоичных данных.

```bsl
// Из файла на диске
Письмо.Вложения.Добавить("C:\temp\Счёт.xlsx");

// Из двоичных данных (например, только что сформированного отчёта)
ДанныеОтчёта = Новый ДвоичныеДанные("C:\temp\Отчёт.pdf");
Письмо.Вложения.Добавить(ДанныеОтчёта, "Отчёт.pdf");
```

> **Важно.** Путь к файлу ищется **на сервере 1С**, а не на компьютере пользователя. На клиенте этот код надо выполнять на сервере (директива `&НаСервере`) или предварительно переносить файл на сервер.

## Шаг 4. Отправка по расписанию

Чтобы письмо уходило само (утренний отчёт, напоминание), положите отправку в **[регламентное задание](/glossary/#reglamentnoe-zadanie)**. Например, формируем отчёт, сохраняем его в файл и прикладываем:

```bsl
ТабличныйДокумент = Новый ТабличныйДокумент;
// ... здесь заполняем отчёт ...
Путь = ПолучитьИмяВременногоФайла("xlsx");
ТабличныйДокумент.Записать(Путь, ТипФайлаТабличногоДокумента.XLSX);

// дальше — тот же код отправки, что в Шаге 2
Письмо.Вложения.Добавить(Путь, "Отчёт.xlsx");
```

Как настраивать само расписание — в статье [«Регламентные задания в 1С: настройка и контроль»](/cheats/scheduled-jobs-1c/).

## Шаг 5. Где хранить пароль

Не храните пароль прямо в тексте модуля — его увидят все, у кого есть доступ к коду и к хранилищу.

- Правильный путь — использовать штатный механизм **«Настройки почты»** (в типовых конфигурациях на базе БСП) и **безопасное хранилище паролей**.
- Если пишете проще — заведите константу с паролем и закройте её от просмотра, но помните: это компромисс, а не решение.

## Типовые грабли

> - **Ошибка авторизации `535`.** Обычный пароль не подходит — сделайте пароль приложения.
> - **Порт и шифрование не совпадают.** Для 465 ставьте `ИспользоватьSSLSMTP = Истина`; для 587 (STARTTLS) — `Ложь`.
> - **Нет доступа в интернет у сервера 1С.** Проверьте прокси и firewall: `Подключиться` будет «висеть» и падать по таймауту.
> - **Кириллица в теме или тексте «кракозябрами».** Явно задайте `Письмо.Кодировка = КодировкаТекста.UTF8`.
> - **Файл вложения не найден.** Сервер 1С не видит диск пользователя — держите файл там, куда есть доступ у сервера.
> - **Логин и пароль только латиницей.** Поля `ПользовательSMTP`/`ПарольSMTP` — только US-ASCII.
> - **Провайдер ограничивает рассылку.** При массовых отправках ставьте задержку и следите за лимитами.

## Куда развивать

- Приём входящих писем через POP3/IMAP (`Подключиться(Профиль, ПротоколИнтернетПочты.IMAP)`).
- Шаблоны писем с подстановкой данных вместо склеивания строк.
- Использование штатной подсистемы БСП «Почта» и безопасного хранилища паролей.
- Надёжная отправка с повторами и логом — по образцу [«Исходящая очередь: надёжная отправка во внешние системы»](/cheats/outgoing-queue-1c/).

Сразу после установки «из коробки» почти всё умеет только администратор. Чтобы пользователи могли работать, а лишнего не видели, в 1С настраивают **права доступа**: кто какие объекты видит и меняет. Разберём, как это устроено и как ограничить доступ к отдельным данным.

## Что такое права доступа и RLS

**Права доступа** — это разрешения на действия с объектами: читать справочник, добавлять документы, проводить, удалять. Их не выдают пользователю по одному — их собирают в **[роли](/glossary/#rol)**, а роли — в **[профили](/glossary/#profil)**.

**[RLS](/glossary/#rls)** (от англ. Row-Level Security) — это ограничение доступа не ко всему объекту, а к отдельным **записям**. Простой пример: все менеджеры работают в одном справочнике «Клиенты», но каждый видит только своих.

```
Пользователь  -->  Профиль  -->  Роли  -->  Права на объекты + RLS
```

## Когда это нужно

- Добавили новый справочник или документ — сразу продумайте права, иначе пользователи его не увидят.
- В компании разные роли: менеджер, кладовщик, бухгалтер — у каждого свой набор.
- Нужно ограничить видимость: «свой склад», «свои документы», «свой филиал».

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| Право доступа | Разрешение на действие с объектом: Чтение, Добавление, Изменение, Удаление, Проведение. |
| Роль | Набор прав под одну простую задачу, например «Изменение заказов». |
| Профиль | Набор ролей, который назначают пользователю. |
| Пользователь | Учётная запись для входа в программу. |
| RLS | Ограничение доступа к отдельным записям данных, а не ко всему объекту. |
| Параметр сеанса | Значение, доступное во время сеанса (например, текущий пользователь) — в том числе внутри запросов. |
| Привилегированный режим | Выполнение кода без проверки прав. |

## Что понадобится

- Конфигуратор и права администратора.
- Понимание, какие роли нужны именно вам (обычно подсказывает бизнес: «кто что делает»).

## Шаг 1. Роли и профили: как устроено

Схема простая: **пользователю назначают профиль, в профиле лежат роли, в ролях — права**.

Так одну и ту же роль можно выдать многим людям, а сотруднику — собрать набор ролей под его работу.

> **Правило.** Одна роль = одна элементарная функция: «Чтение номенклатуры», «Изменение заказов». Не делайте «толстых» ролей «на всё сразу» — их неудобно выдавать и проверять.

## Шаг 2. Права на объект: две роли

Для большинства объектов по стандарту делают **две** роли:

- `...Чтение` — только просмотр.
- `...ДобавлениеИзменение` — просмотр, добавление и изменение (изменение включает в себя чтение).

Пример имён: `ЧтениеНоменклатуры` и `ДобавлениеИзменениеНоменклатуры`.

> **Важно.** Не выдавайте обычным пользователям **интерактивное удаление**. Удаление помеченных объектов делают отдельной ролью — так данные можно случайно не стереть.

## Шаг 3. Ограничение доступа к записям (RLS)

RLS — это условие в правах роли, которое платформа подставляет в запросы. Классика: «пользователь видит только свои документы».

Порядок такой:

1. Завести **[параметр сеанса](/glossary/#parametr-seansa)** (например, `ТекущийПользователь`).
2. Устанавливать его в модуле сеанса, в обработчике `УстановкаПараметровСеанса`.
3. Использовать этот параметр в ограничении доступа роли.

```bsl
// Модуль сеанса. Параметр устанавливается «по требованию»,
// когда платформа его запросит (а не при старте).
Процедура УстановкаПараметровСеанса(ТребуемыеПараметры)
    Если ТребуемыеПараметры.Найти("ТекущийПользователь") <> Неопределено Тогда
        УстановитьЗначениеПараметраСеанса("ТекущийПользователь", Пользователи.ТекущийПользователь());
    КонецЕсли;
КонецПроцедуры
```

Теперь в **ограничении доступа** роли (в конфигураторе, на вкладке «Ограничения доступа к данным») пишем условие:

```sql
ГДЕ Документ.Автор = &ТекущийПользователь
```

Так менеджер увидит только свои документы. Отдельное право на объект для этого не требуется.

> **Важно.** Параметры сеанса устанавливайте «по требованию», а не при старте сеанса: иначе это бьёт по скорости, особенно при RLS.

## Шаг 4. Проверка прав в коде

Если что-то нужно спрятать или показать в интерфейсе — проверяйте право на объект, а не название роли:

```bsl
Если ПравоДоступа("Редактирование", Метаданные.Справочники.Номенклатура) Тогда
    // показать кнопку изменения
КонецЕсли;
```

> **Неверно.** `РольДоступна("ДобавлениеИзменениеНоменклатуры")` — так проверять нельзя: роль это «деталь сборки», её состав и имя могут измениться. `РольДоступна` годится только для ролей-маркеров, у которых нет прав на объекты.

## Шаг 5. Обязательные (стандартные) роли

В конфигурации по стандартам должны быть три роли:

- `ПолныеПрава` — неограниченный доступ к прикладным данным.
- `АдминистраторСистемы` — системное администрирование (назначается только вместе с `ПолныеПрава`).
- `ИнтерактивноеОткрытиеВнешнихОтчетовИОбработок` — открытие внешних отчётов и обработок.

Их указывают в свойстве конфигурации **«Основные роли»**. Интерактивное удаление — отдельная роль «Удаление помеченных объектов».

> **Важно.** `ПолныеПрава` намеренно **не** даёт интерактивное удаление — это защита от случайного стирания данных.

## Типовые грабли

> - **Все права в одной огромной роли.** Разбивайте по функциям, иначе нельзя выдать «половину» прав.
> - **Проверка через `РольДоступна`.** Используйте `ПравоДоступа` — роли можно переименовать или перегруппировать.
> - **Ролевая видимость элементов формы.** При большом числе ролей замедляет открытие форм — делайте отдельные формы или проверяйте права в коде.
> - **RLS без параметра сеанса.** Ограничение не сработает, если параметр не установлен.
> - **Фейковое право `ГДЕ ЛОЖЬ`** «для проверки роли» — так нельзя; проверяйте роль.
> - **Забыли про привилегированный режим.** Для проведения документов и получения функциональных опций есть отдельные требования.
> - **Дают интерактивное удаление пользователям.** Не давайте; удаление помеченных — отдельная роль.

## Куда развивать

- Профили и назначение пользователей — штатная подсистема БСП «Пользователи».
- RLS на больших объёмах требует внимания к производительности: чем сложнее условие, тем медленнее запросы.
- Внешние системы и их авторизация — см. [«Приём входящих через HTTP-сервис: свой REST с нуля»](/cheats/http-service-1c/).

Многие задачи должны выполняться сами, без человека: обновить курсы, разослать отчёты, пересчитать остатки. В 1С для этого есть **[регламентные задания](/glossary/#reglamentnoe-zadanie)** — процедуры, которые платформа запускает по расписанию. Разберём, как их создать и не наступить на грабли.

## Что такое регламентное задание и когда это нужно

**Регламентное задание** — это ваш код (процедура), который платформа запускает на сервере по заданному расписанию. Вы один раз настраиваете «что делать» и «когда», дальше оно работает само.

Когда это нужно:

- периодические действия: обновление данных, рассылки, пересчёты;
- обслуживание: чистка временных файлов, проверки целостности;
- отложенная обработка, которую нельзя делать в момент работы пользователя.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| Регламентное задание | Настройка «что и когда запускать». |
| Обработчик | Процедура, которую выполняет задание. |
| Имя метода | Строка вида `ОбщийМодуль.Процедура`, указывающая на обработчик. |
| Расписание | Правило запуска: как часто и в какое время. |
| **[Фоновое задание](/glossary/#fonovoe-zadanie)** | Один фактический запуск обработчика (экземпляр выполнения). |
| Предопределённое задание | Задание, созданное в конфигурации; существует в базе автоматически. |

## Что понадобится

- Конфигуратор и права администратора.
- Общий модуль на сервере для кода задания.
- (Желательно) конфигурация на БСП — там уже есть готовая подсистема «Регламентные задания».

## Шаг 1. Создать задание в конфигураторе

1. Откройте ветку **Регламентные задания** и добавьте новое.
2. Заполните **Наименование** (понятное людям) и **Имя метода** — например, `МоиЗадачи.ОбновитьКурсы`.
3. Поставьте флажок **Использование** (иначе задание не запустится).
4. Настройте **Расписание** (см. Шаг 3).

> **Важно.** Если задание предопределённое (создано в конфигурации), не задавайте его наименование вручную в коде — оно берётся из метаданных.

## Шаг 2. Написать обработчик

Обработчик — **экспортная процедура** в **общем модуле** (сервер, без контекста клиента). В начале процедуры в конфигурациях на БСП обязателен вызов `ОбщегоНазначения.ПриНачалеВыполненияРегламентногоЗадания()` — он не даёт заданию выполниться, пока идёт обновление базы.

```bsl
// Общий модуль "МоиЗадачи". Процедура экспортная, без контекста.
Процедура ОбновитьКурсы() Экспорт

    // Защита: если база на обновлении — задание прервётся.
    ОбщегоНазначения.ПриНачалеВыполненияРегламентногоЗадания();

    Попытка
        // ... здесь полезная работа ...
    Исключение
        ЗаписьЖурналаРегистрации(
            "МоиЗадачи.ОбновитьКурсы",
            УровеньЖурналаРегистрации.Ошибка,
            , ,
            ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
        ВызватьИсключение;
    КонецПопытки;

КонецПроцедуры
```

> **Проверка.** Сделайте в обработчике простую запись в журнал регистрации и запустите задание вручную (Шаг 4): если запись появилась — обработчик подключён верно.

## Шаг 3. Настроить расписание

Расписание настраивается в форме задания в конфигураторе. Программно его можно задать так:

```bsl
Задание = РегламентныеЗадания.НайтиПредопределенное(Метаданные.РегламентныеЗадания.МоиЗадачи);

Расписание = Новый РасписаниеРегламентногоЗадания;
Расписание.ПериодПовтораДней = 1;          // раз в день
Расписание.ВремяНачала        = Дата("20240101070000"); // в 07:00

Задание.Расписание     = Расписание;
Задание.Использование  = Истина;
Задание.Записать();
```

Основные «ручки» расписания: `ПериодПовтораВТечениеДня` (в секундах), `ПериодПовтораДней`, `ПериодНедель`, `ДниНедели`, `ДеньВМесяце`, `ВремяНачала`.

> **Важно.** Не ставьте периодичность чаще раза в минуту — это создаёт лишнюю нагрузку и считается ошибкой настройки.

## Шаг 4. Запустить вручную (для проверки)

Работа системы не должна зависеть только от автоматического запуска: администратор должен уметь запустить задание вручную. Пример (с защитой от повторного запуска, если задание уже выполняется):

```bsl
ИмяМетода = Метаданные.РегламентныеЗадания.МоиЗадачи.ИмяМетода;

Отбор = Новый Структура;
Отбор.Вставить("ИмяМетода", ИмяМетода);
Отбор.Вставить("Состояние", СостояниеФоновогоЗадания.Активно);

Если ФоновыеЗадания.ПолучитьФоновыеЗадания(Отбор).Количество() = 0 Тогда
    ФоновыеЗадания.Выполнить(ИмяМетода, , , "МоиЗадачи");
КонецЕсли;
```

> **Совет.** В типовых на БСП для этого уже есть готовая форма «Регламентные и фоновые задания» — не пишите свой интерфейс, если он не нужен.

## Шаг 5. Следить за выполнением

Результат последнего запуска лежит в свойстве задания:

```bsl
Задание = РегламентныеЗадания.НайтиПредопределенное(Метаданные.РегламентныеЗадания.МоиЗадачи);

Если Задание.ПоследнееЗадание <> Неопределено Тогда
    Состояние = Задание.ПоследнееЗадание.Состояние; // ЗавершеноУспешно, ЗавершеноАварийно, Активно
    Ошибка   = Задание.ПоследнееЗадание.ИнформацияОбОшибке;
КонецЕсли;
```

Ошибки задания также попадают в журнал регистрации — поэтому `ЗаписьЖурналаРегистрации` в обработчике обязательна.

## Типовые грабли

> - **Нет вызова `ОбщегоНазначения.ПриНачалеВыполненияРегламентногоЗадания()`.** Задание может начать работу прямо во время обновления базы — это ошибка уровня «обязательно».
> - **Обработчик не экспортный или с контекстом.** Регламентное задание запускается на сервере; процедура должна быть экспортной и без клиентского контекста.
> - **Расписание чаще раза в минуту.** Такую периодичность задавать нельзя — лишняя нагрузка.
> - **Задание «накладывается» само на себя.** Долгий запуск может идти, пока стартует следующий — проверяйте активные фоновые задания.
> - **Падение молча.** Без `Попытка ... Исключение` и записи в журнал вы не узнаете, что задание падало.
> - **Только авто-запуск.** Дайте возможность ручного запуска: на кластере задания могут быть отключены, а в файловой базе авто-выполнения может не быть вовсе.
> - **Наименование предопределённого задают в коде.** Его берут из метаданных, а не пишут руками.

## Куда развивать

- Штатная подсистема БСП «Регламентные задания» — расписания, ручной запуск, история.
- Пример применения: отправка отчёта по расписанию — см. [«Почта из 1С: настройка и отправка писем (SMTP)»](/cheats/email-smtp-1c/).
- Надёжная отправка во внешние системы с повторами — см. [«Исходящая очередь: надёжная отправка во внешние системы»](/cheats/outgoing-queue-1c/).
- Длительные операции на сервере с прогрессом для пользователя.

Когда 1С «тормозит», а по [журналу регистрации](/glossary/#zhurnal-registratsii) ничего не видно, на помощь приходит **[технологический журнал](/glossary/#tehzhurnal)**. Это технический лог самой платформы: он показывает, какие запросы выполнялись долго, где были таймауты блокировок и какие ошибки ловил сервер. Разберём, как его включить и прочитать.

## Что такое технологический журнал и когда его включать

**Технологический журнал** (часто называют по имени файла настройки — **logcfg**) — это механизм платформы 1С, который пишет в текстовые файлы «внутреннюю жизнь» сервера: время выполнения запросов, обращения к серверу базы данных, таймауты блокировок, исключения.

Это **инструмент диагностики**, а не постоянный режим работы:

- включают на время разбора проблемы (медленно, зависает, ошибки);
- затем **обязательно выключают** — журнал заметно нагружает сервер и быстро занимает диск.

> **Важно.** Состав событий, их свойства и уровни зависят от версии платформы. Перед настройкой сверяйтесь с документацией ИТС — здесь приведён базовый пример.

## Чем отличается от журнала регистрации

Это частая путаница, поэтому сразу:

| | Журнал регистрации | Технологический журнал |
| --- | --- | --- |
| О чём | Бизнес-события: кто что сделал в программе | Технические события платформы и сервера |
| Где смотреть | В самой 1С (Администрирование) | В текстовых файлах / Центре управления производительностью |
| Включать всегда? | Да, работает постоянно | Нет, только на время диагностики |

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| logcfg | Файл `logcfg.xml`, которым задаётся, что писать в техжурнал. |
| Событие | Тип записи: исключение, таймаут блокировки, запрос и т.д. |
| EXCP | События об исключениях (ошибках). |
| TLOCK | Таймауты управляемых блокировок. |
| DBMSQL / DBPOSTGRS | Обращения к серверу базы данных (MS SQL / PostgreSQL). |
| SDBL | Выполнение запросов на стороне сервера приложений. |
| ЦУП | Центр управления производительностью — приложение для сбора и анализа техжурнала. |

## Что понадобится

- Доступ к серверу, где стоит сервер 1С (каталог установки платформы).
- Права администратора сервера.
- Достаточно места на диске под логи.
- Понимание, что именно вы ищете: медленные запросы, блокировки или ошибки.

## Шаг 1. Где включается

Настройка задаётся файлом **`logcfg.xml`**, который кладут в каталог **`conf`** каталога установки платформы (рядом с исполняемыми файлами, например `C:\Program Files\1cv8\conf\`). Файл читается сервером 1С при старте, поэтому после правки службу сервера перезапускают.

Удобнее работать через **Центр управления производительностью (ЦУП)**: он ставится отдельно, сам формирует настройки и умеет показывать медленные запросы и блокировки без ручного разбора файлов.

## Шаг 2. Пример logcfg.xml

Минимальный файл, который пишет ошибки и таймауты блокировок (и складывает логи в папку `C:\1c_tech_log`):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="C:\1c_tech_log" history="4" format="text">

    <!-- Ошибки и исключения -->
    <event>
      <eq property="name" value="EXCP"/>
      <property name="all"/>
    </event>

    <!-- Таймауты управляемых блокировок -->
    <event>
      <eq property="name" value="TLOCK"/>
      <property name="all"/>
    </event>

  </log>
</config>
```

Для разбора медленных запросов добавляют события обращений к базе — например, `DBPOSTGRS` (PostgreSQL) или `DBMSSQL` (MS SQL).

> **Важно.** Чем больше событий и свойств (`all`), тем объёмнее и «тяжелее» журнал. Начинайте с минимума под конкретную задачу.

## Шаг 3. Включить, собрать, выключить

1. Создайте `logcfg.xml` в каталоге `conf`.
2. Перезапустите службу сервера 1С.
3. Воспроизведите проблему (дайте пользователям поработать, пока «тормозит»).
4. Соберите логи из указанного каталога.
5. **Удалите `logcfg.xml`** и перезапустите службу, чтобы вернуть обычный режим. Логи при необходимости сохраните отдельно.

## Шаг 4. Как читать

Логи — это текстовые файлы, в имени которых обычно есть дата, время и имя процесса (например, `rphost`). Строка содержит время, длительность, тип события и данные.

На что смотреть:

- **EXCP** — текст исключения и стек: что именно упало.
- **TLOCK** — какая блокировка и какой длительности: ищите «долгие» удержания и взаимные блокировки.
- **DBPOSTGRS / DBMSSQL / SDBL** — длительность (`duration`, `ttime`) запросов: найдите самые долгие и посмотрите их текст.

> **Совет.** Не пытайтесь читать сотни мегабайт глазами — используйте ЦУП или простой поиск по максимальным значениям длительности.

## Типовые грабли

> - **Оставили журнал включённым.** Техжурнал нагружает сервер и быстро съедает диск — только на время диагностики.
> - **Включили «всё подряд».** Событие `all` по многим типам даёт гигантский объём; берите минимум под задачу.
> - **Правили `logcfg.xml`, но не перезапустили сервер.** Настройка читается при старте — изменения не применятся.
> - **Ищут бизнес-события в техжурнале.** Кто удалил документ — это журнал регистрации; техжурнал про другое.
> - **Забыли про версию платформы.** Набор событий и свойства различаются между версиями — сверяйтесь с ИТС.
> - **Разбирают только запросы, забыв про блокировки.** «Тормоза» часто из-за TLOCK, а не из-за тяжёлого запроса.

## Куда развивать

- Центр управления производительностью (ЦУП) — сбор, обзорные отчёты и поиск проблем.
- Разбор запросов из событий `SDBL`/`DBPOSTGRS` — см. [«Приём входящих через HTTP-сервис: свой REST с нуля»](/cheats/http-service-1c/) для отладки своих сервисов.
- Постоянный контроль ошибок (без техжурнала) — через журнал регистрации и подсистемы БСП.

Веб-сервис — это способ отдать функции 1С наружу или вызвать чужие, когда обе стороны строго описывают данные в [XML](/glossary/#xml). Используется там, где важен формальный контракт: банки, гос. системы, старые корпоративные API. Разберём, как опубликовать свой сервис и как подключиться к чужому.

## Что такое веб-сервис и SOAP

**[SOAP](/glossary/#soap)** — протокол обмена структурированными XML-сообщениями. В 1С он реализуется объектом **веб-сервис** (`ws/...`). Описание сервиса хранится в **[WSDL](/glossary/#wsdl)** — это XML, где перечислены операции, их параметры и типы.

Главное отличие от [HTTP-сервиса](/cheats/http-service-1c/) (REST/JSON): у SOAP строгая типизация через **[XDTO](/glossary/#xdto)**, а обмен идёт XML, а не JSON. Выбирайте SOAP, когда контрагент требует именно его, иначе проще REST.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| SOAP | протокол обмена XML-сообщениями |
| WSDL | XML-описание сервиса: операции, параметры, типы |
| Веб-сервис | объект 1С, публикуемый наружу по адресу `ws/...` |
| [WS-прокси](/glossary/#ws-proksi) | объект 1С для вызова *чужого* сервиса |
| XDTO | механизм типизации данных в XML |

## Публикуем свой веб-сервис

1. В Конфигураторе: **Общие → Веб-сервисы → Добавить**. Задайте имя (например, `СправочнаяИнформация`) и URI пространства имён (например, `http://mycompany.ru/ws`).
2. Добавьте **операцию** (например, `ПолучитьКурсВалюты`), укажите возвращаемый тип и параметры. Типы должны быть из ветки XDTO.
3. Опишите логику в модуле веб-сервиса:

```bsl
Функция ПолучитьКурсВалюты(КодВалюты) Экспорт

    Запрос = Новый Запрос;
    Запрос.Текст =
    "ВЫБРАТЬ
    |    КурсыВалют.Курс
    |ИЗ
    |    РегистрСведений.КурсыВалют КАК КурсыВалют
    |ГДЕ
    |    КурсыВалют.Валюта.Код = &Код";
    Запрос.УстановитьПараметр("Код", КодВалюты);
    Результат = Запрос.Выполнить().Выбрать();

    Если Результат.Следующий() Тогда
        Возврат Результат.Курс;
    КонецЕсли;

    Возврат Неопределено;

КонецФункции
```

4. Опубликуйте базу на веб-сервере с галочкой **«Публиковать веб-сервисы»** (см. [«Публикация на Apache»](/cheats/apache-publish-1c/) или [«Публикация на IIS»](/cheats/iis-publish-1c/)).

> **Проверка.** Откройте в браузере `http://localhost/erp/ws/СправочнаяИнформация?wsdl` — должен отдаться XML с описанием операций.

## Вызываем чужой веб-сервис

1. Узнайте адрес WSDL чужого сервиса.
2. Конфигуратор → **Общие → WS-ссылки → Добавить**, вставьте URL WSDL. 1С подтянет список операций и создаст прокси.
3. Вызывайте в коде через созданный прокси:

```bsl
// Создаём прокси и указываем настройки подключения
Прокси = WSСсылки.ЧужойСервис.СоздатьWSПрокси(
    "http://www.w3.org/2003/05/soap-envelope",
    "http://чужая-система/ws/Сервис",
    "СервисSoap");

Прокси.Пользователь = "user";
Прокси.Пароль = "pass";

Курс = Прокси.ПолучитьКурс("USD");
```

> **Проверка.** Выполните код и убедитесь, что переменная `Курс` заполнена.

## Типовые грабли

- **Не совпадают типы.** Параметры операции должны быть XDTO-типами, а не обычными типами 1С. Если операция не создаётся — проверьте тип.
- **Ошибка `WSDL не найден`.** Проверьте, что база опубликована с веб-сервисами и адрес набран точно.
- **Пространство имён.** Убедитесь, что URI пространства имён уникален — от него зависит адрес WSDL.
- **Права.** Для доступа к веб-сервису пользователю нужны права на его операции.

«Конвертация данных 2.0» (КД 2.0) — типовой инструмент 1С для настройки обмена между **разными** конфигурациями: например, перенести справочники из УТ в самописную базу. Вы не пишете код — вы описываете **правила конвертации**, а КД выполняет обмен по ним.

> **Факт.** Инструмент «Конвертация данных 2.0» поставщиком больше не развивается и не обновляется: новых возможностей и исправлений в него не добавляют. Всё описанное ниже применимо к уже существующим правилам и обменам.

## Что такое КД 2.0 и правила

**[КД 2.0](/glossary/#kd20)** работает на трёх видах правил:

- **[КО](/glossary/#ko-pko-pvd)** — правила конвертации объектов: как объект одной базы превращается в объект другой (например, «Контрагент → Партнёр»).
- **[ПКО](/glossary/#ko-pko-pvd)** — правила конвертации свойств: как сопоставляются реквизиты (например, `Наименование` → `Название`).
- **[ПВД](/glossary/#ko-pko-pvd)** — правила выгрузки данных: какие объекты и по какому отбору выгружать.

Дополнительно бывают правила «событий» (код до/после) — для нестандартных случаев.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| КД 2.0 | типовой инструмент настройки обменов по правилам |
| КО | правило конвертации объекта |
| ПКО | правило конвертации свойства |
| ПВД | правило выгрузки данных |
| Универсальный формат | стандарт обмена между типовыми конфигурациями |
| [EnterpriseData](/glossary/#enterprisedata) | формат обмена, на котором основана КД 3.0 |
| ВПФ | внутренний идентификатор объекта |

> **Важно.** Если обе базы типовые (БП ↔ ЗУП), обмен уже настроен на **[Универсальном формате](/glossary/#universalnyy-format)**. КД 2.0 нужен в первую очередь для нестандартных пар баз.

## КД 2.0 и КД 3.0

| | КД 2.0 | [КД 3.0](/cheats/conversion-rules-3-1c/) |
| --- | --- | --- |
| Что это | внешняя обработка с собственными правилами конвертации | конвертация данных на основе формата EnterpriseData |
| Как задаются правила | КО / ПКО / ПВД | правила конвертации над структурами EnterpriseData |
| Формат обмена | собственный (правила + файлы выгрузки) | [EnterpriseData](/glossary/#enterprisedata) (пакеты XDTO) |
| Обновляется поставщиком | нет | — |

> **Требование стандарта.** «Новые обмены на основе правил конвертации не разрабатывайте» — [std771 «Интеграция прикладных решений через формат EnterpriseData»](https://v8std.ru/std/771/). Обмен между конфигурациями на БСП выполняется на основе формата EnterpriseData.

## Что понадобится

1. База-приёмник и база-источник (можно две пустые конфигурации для пробы).
2. Внешняя обработка «Конвертация данных 2.0» — файл `.epf` из комплекта поставки 1С или с ИТС (раздел про конвертацию данных).

## Шаг 1. Выгрузите описания метаданных

В каждой базе откройте внешнюю обработку и выполните выгрузку описания метаданных (в обработке это команды выгрузки/загрузки структуры конфигурации). Получатся файлы с описанием справочников, документов и их реквизитов. Затем загрузите эти файлы в обработку — по ним КД строит соответствие объектов и свойств.

## Шаг 2. Создайте правила конвертации

В КД задайте соответствие объектов (КО) и свойств (ПКО):

- `Справочник.Контрагенты` → `Справочник.Партнёры`;
- реквизит `Наименование` → `Наименование`;
- реквизит `ИНН` → `ИНН`.

Для ссылочных реквизитов укажите, что искать по **[ВПФ](/glossary/#vpf)** (внутреннему идентификатору), чтобы объекты корректно связывались.

**Сквозной пример.** Нужно перенести контрагентов из базы-источника в базу-приёмник: в КО сопоставляем справочники «Контрагенты» → «Партнёры», в ПКО — реквизиты (`Наименование`, `ИНН`). Для реквизита-ссылки «Основной менеджер» задаём поиск по ВПФ, чтобы менеджер нашёлся в приёмнике и связался с контрагентом. В ПВД указываем отбор — например, «только действующие контрагенты».

## Шаг 3. Сохраните правила и запустите обмен

Правила сохраняются в файл XML. Затем обмен выполняется либо через обработку КД, либо через штатные механизмы:

1. Создайте **план обмена** (если обмен постоянный) — см. [«РИБ и планы обмена»](/cheats/distributed-info-base-1c/).
2. Либо разово: выгрузите данные по ПВД, перенесите файл, загрузите в приёмник по правилам.

> **Проверка.** После загрузки откройте справочник в приёмнике — записи должны появиться с заполненными реквизитами и корректными связями.

## Типовые грабли

- **Не заполняются ссылки.** Проверьте, что для ссылочных свойств указан поиск по ВПФ, иначе связи теряются.
- **Разный состав реквизитов.** Для отсутствующих в приёмнике реквизитов задайте значение по умолчанию в ПКО.
- **Дубли при повторной загрузке.** Настройте поиск существующего объекта по уникальному ключу (код, ИНН).
- **Данные не выгружаются.** Проверьте отбор в ПВД — возможно, он пустой.
- **Инструмент больше не обновляется поставщиком.** Новые возможности и исправления в КД 2.0 не добавляются.

Распределённая информационная база (РИБ) нужна, когда несколько подразделений работают автономно, а потом периодически синхронизируются: центральный офис и филиалы без постоянной связи. Данные переносятся по **планам обмена** через файлы или сеть.

## Что такое РИБ и план обмена

**[РИБ](/glossary/#rib)** — схема, при которой одна конфигурация живёт в нескольких базах-**[узлах](/glossary/#uzel)**, а данные между ними переносятся по **[плану обмена](/glossary/#plan-obmena)**. План обмена — объект конфигурации, который описывает, какие данные переносить и между кем.

Отличие от [КД 2.0](/cheats/conversion-rules-1c/): РИБ работает с **одинаковыми** конфигурациями и встроен в платформу, КД — с разными.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| РИБ | распределённая информационная база |
| План обмена | объект, описывающий состав и правила обмена |
| Узел | отдельная база-участник РИБ |
| Авторегистрация | автоматическая пометка изменений к выгрузке |
| ВПФ | внутренний идентификатор объекта |

## Шаг 1. Создайте план обмена

В Конфигураторе: **Общие → Планы обмена → Добавить**. Назовите, например, `ОбменДанными`. На вкладке «Состав» отметьте объекты, которые будут обмениваться (справочники, документы).

## Шаг 2. Включите авторегистрацию

В свойствах объектов в составе плана обмена включите **[авторегистрацию](/glossary/#avtoregistratsiya)**. Тогда при изменении объекта он сам помечается «к выгрузке» — регистрировать изменения вручную не нужно.

## Шаг 3. Создайте узлы и образ периферийной базы

1. В главной базе создайте предопределённые узлы для каждого филиала.
2. Через «Создать начальный образ» сформируйте файл-образ периферийной базы.
3. Разверните его в филиале.

## Шаг 4. Выполните обмен

Обмен делается через планы обмена. Минимальный код — чтение изменений и их отправка:

```bsl
// Выгрузка изменений для узла
Узел = ПланыОбмена.ОбменДанными.НайтиПоКоду("Филиал1");
Запись = ПланыОбмена.СоздатьЗаписьСообщения();
Запись.НачатьЗапись(ЗаписьСообщения(), Узел);
// ... формирование сообщения ...

// Загрузка полученного сообщения
Запись.ПрочитатьСообщение(ЗаписьСообщения());
```

На практике часто используют готовую обработку «Универсальный обмен данными в формате XML» либо штатные механизмы типовых конфигураций.

> **Проверка.** Измените объект в филиале, выполните обмен и убедитесь, что изменение пришло в центральную базу (и наоборот).

## Типовые грабли

- **Обмен идёт, но данных нет.** Проверьте, включена ли авторегистрация у объектов и у всех ли.
- **Дубли объектов.** Следите за тем, чтобы обмен не выполнялся одновременно в обе стороны без контроля — используйте блокировку узла.
- **Разные коды узлов.** Код узла должен быть уникальным и одинаковым во всех базах.
- **Изменения не регистрируются.** Проверьте права и то, что объект входит в состав плана обмена.

- Обмен между разными конфигурациями — [«КД 2.0»](/cheats/conversion-rules-1c/).
- Обмен между типовыми через Универсальный формат.
- Незнакомые термины — [Глоссарий](/glossary/).

Публикация на **[IIS](/glossary/#iis)** — способ открыть базу 1С по HTTP под Windows: тонкий клиент, HTTP-сервисы, OData и веб-сервисы. Альтернатива — [Apache](/cheats/apache-publish-1c/); IIS чаще используют, когда он уже есть в инфраструктуре Windows.

## Что такое IIS и ISAPI

**[IIS](/glossary/#iis)** (Internet Information Services) — веб-сервер Microsoft. 1С подключается к нему через интерфейс **[ISAPI](/glossary/#isapi)** модулем `wsisapi.dll`. Публикация выполняется в **[пул приложений](/glossary/#pul-prilozheniy)** — изолированный процесс с определённой разрядностью.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| IIS | веб-сервер от Microsoft |
| ISAPI | интерфейс IIS, через который работает модуль 1С |
| Пул приложений | изолированный процесс выполнения публикации |
| webinst | утилита публикации из командной строки |

## Шаг 1. Включите IIS

Откройте «Панель управления → Программы и компоненты → Включение компонентов Windows» и отметьте:

- **Службы IIS → Компоненты разработки приложений → ISAPI-расширения**;
- **Службы IIS → Веб-инструменты управления → Консоль управления IIS**.

## Шаг 2. Опубликуйте базу из Конфигуратора

1. Откройте базу в Конфигураторе.
2. **Администрирование → Публикация на веб-сервере**.
3. Выберите веб-сервер **IIS**, имя публикации (например, `erp`), каталог.
4. Отметьте, что публиковать: HTTP-сервисы, OData, веб-сервисы, тонкий клиент.
5. Задайте имя **пула приложений** и разрядность (должна совпадать с разрядностью 1С).

> **Проверка.** Откройте `http://localhost/erp/` — должна открыться страница публикации 1С. OData доступен по `http://localhost/erp/odata/standard.odata`.

## Шаг 3. Публикация из командной строки (webinst)

То же самое без Конфигуратора делает утилита **[webinst](/glossary/#webinst)**:

```bat
webinst.exe -publish -iis -wsdir erp -dir "C:\inetpub\wwwroot\erp" -connstr "Srvr=server;Ref=base;" -descriptor "...\v8iis.dll"
```

> **Проверка.** Команда завершается без ошибок, каталог публикации создан, сайт виден в IIS.

## Типовые грабли

- **Ошибка 500 / 401.** Проверьте права пользователя пула приложений на каталог публикации и базу.
- **Разрядность.** Разрядность пула приложений (32/64) должна совпадать с разрядностью платформы 1С.
- **ISAPI не включён.** Если публикация не работает — проверьте компонент ISAPI-расширения в компонентах Windows.
- **Неверная строка соединения.** Проверьте `Srvr`/`Ref` в строке соединения — имя базы должно совпадать.

Когда база работает в клиент-серверном режиме, её серверный код выполняет не один процесс, а **[кластер](/glossary/#klaster)** — группа серверов и рабочих процессов. Понимание его устройства нужно, чтобы находить «куда ушла память» и почему база тормозит.

## Что такое кластер и его процессы

**[Кластер](/glossary/#klaster)** состоит из серверов, на каждом из которых работает служба-**[агент ragent](/glossary/#ragent)**. Агент управляет рабочими процессами **[rphost](/glossary/#rphost)** — именно они выполняют код 1С. **[Центральный сервер](/glossary/#tsentralnyy-server)** хранит реестр кластера (базы, сеансы, блокировки) и координирует остальных.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| Кластер | группа серверов и процессов, выполняющих серверный код |
| Центральный сервер | хранит реестр и управляет кластером |
| ragent | агент, управляющий рабочими процессами на сервере |
| rphost | рабочий процесс, выполняющий код сеансов |
| Сеанс | активная работа пользователя |
| Соединение | канал связи с базой (у сеанса их может быть несколько) |

## Шаг 1. Откройте консоль кластера

Установите «Администрирование серверов 1С» (консоль кластера) и подключитесь к центральному серверу. Здесь видны:

- **Центральные серверы** и список рабочих серверов;
- **Информационные базы** и их сеансы/соединения;
- **Рабочие процессы** (rphost) и их загрузка.

## Шаг 2. Посмотрите сеансы и соединения

- **[Сеанс](/glossary/#seans)** — активная работа пользователя (его интерфейс, контекст).
- **[Соединение](/glossary/#seans)** — канал с базой. У одного сеанса соединений может быть несколько (основное + служебные).

> **Проверка.** Откройте базу в клиенте и убедитесь, что в консоли появился новый сеанс и соединение.

## Шаг 3. Найдите «тяжёлый» процесс

В списке рабочих процессов (rphost) видно потребление памяти и CPU. Если один rphost съел память — это кандидат на перезапуск или диагностику через **[технологический журнал](/cheats/tech-log-1c/)**.

> **Проверка.** Сравните память rphost до и после выполнения тяжёлого отчёта — по росту видно, кто нагружает процесс.

## Типовые грабли

- **Смешивают сеанс и соединение.** Сеанс = пользователь, соединение = канал. В консоли они в разных разделах.
- **Один rphost ест память.** Включите ТЖ и найдите долгие запросы — см. [«Технологический журнал»](/cheats/tech-log-1c/).
- **Кластер не виден.** Проверьте, что служба агента сервера 1С запущена и порты не закрыты фаерволом.
- **Добавление сервера.** Новый рабочий сервер добавляется в кластер через консоль; без этого он не участвует в работе.

**[Журнал регистрации](/glossary/#zhurnal-registratsii)** — это лог бизнес-событий базы: кто, когда и что делал. По нему отвечают на вопросы «кто удалил документ?», «когда меняли справочник?» и восстанавливают картину происшествий. Не путайте с [технологическим журналом](/cheats/tech-log-1c/) — тот про производительность и ошибки платформы.

## Что такое журнал регистрации

Журнал регистрации фиксирует события: вход/выход пользователей, проведение документов, изменение объектов, ошибки, работу регламентных заданий. Каждая запись содержит дату, пользователя, тип события и данные.

Хранится журнал в специальном файле (`.lgp`) рядом с базой либо в самой ИБ — это настраивается. В клиент-серверном режиме им управляет кластер.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| Журнал регистрации | лог бизнес-событий (кто что делал) |
| Технологический журнал | технический лог производительности и ошибок |
| Кластер | группа серверов, выполняющих серверный код |

## Шаг 1. Откройте журнал

- В Конфигураторе: **Администрирование → Журнал регистрации**.
- В режиме Предприятия (в типовых): **Администрирование → Обслуживание → Журнал регистрации**.

## Шаг 2. Настройте отбор

У журнала есть отбор по периоду, пользователю, типу события и данным. Чтобы не ждать долгую выгрузку:

1. Задайте **период** (например, «за сегодня»).
2. Выберите **тип события** (например, «Удаление»).
3. При необходимости — пользователя или конкретные данные.

> **Проверка.** Задайте отбор по событию «Удаление» за сегодня — список покажет только удаления.

## Шаг 3. Настройте, что писать в журнал

Объём событий настраивается: можно писать только ошибки или всё подряд. Настраивается:

- в Конфигураторе в свойствах объектов и в настройках журнала;
- в типовых — через «Настройки журнала регистрации».

Хранить журнал можно в базе (удобнее искать) или в отдельном файле (быстрее). Компромисс — хранить в базе с регулярной очисткой старых записей.

## Типовые грабли

- **Журнал пуст.** Проверьте, что ведение журнала не отключено и события не отфильтрованы.
- **Долго открывается.** Сузьте период и тип события; старые записи периодически очищайте.
- **Путают с ТЖ.** Журнал регистрации — про события, [технологический журнал](/cheats/tech-log-1c/) — про производительность и технические ошибки.
- **Кто удалил — не видно.** Удаление фиксируется, только если событие включено в журнал.

- Кто и под кем работает — [«Кластер серверов 1С»](/cheats/server-cluster-1c/).

Отладка — это пошаговое выполнение кода, чтобы понять, где он ведёт себя не так. Вместо «Сообщить(...)» в каждой строке ставят **[точку останова](/glossary/#tochka-ostanova)** и смотрят значения переменных в момент выполнения.

## Что понадобится

- Конфигуратор или режим «Отладка по требованию» в Предприятии.
- Понимание, какой модуль и процедура отрабатывают (см. [«Подписки на события»](/cheats/event-subscriptions-1c/), если логика в подписке).

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| Точка останова | место, где выполнение приостанавливается |
| [Табло выражений](/glossary/#tablo-vyrazheniy) | окно значений переменных и вычислений |
| Стек вызовов | цепочка, кто кого вызвал |
| Консоль кода | выполнение кода «на месте» без правки конфигурации |

## Шаг 1. Поставьте точку останова

В Конфигураторе откройте модуль и щёлкните по левому серому полю напротив нужной строки — появится красная точка. Запустите сеанс **с отладкой** (в Конфигураторе: «Отладка → Начать отладку»), затем выполните действие в Предприятии.

> **Проверка.** Выполнение приостановилось на строке с точкой — строка подсвечена жёлтым.

## Шаг 2. Посмотрите значения в табло выражений

Когда выполнение остановлено:

1. Откройте **Табло** (Ctrl+Alt+W) — там видно значения переменных.
2. Введите выражение (например, `Сумма * Ставка`), чтобы вычислить его на лету.
3. Значение можно **изменить** прямо в табло, чтобы проверить другую ветку логики.

## Шаг 3. Пройдитесь по коду

- **F10** (Шаг) — выполнить строку и перейти к следующей.
- **F11** (Шаг с заходом) — зайти внутрь вызываемой процедуры.
- **F5** (Продолжить) — выполнить до следующей точки останова.

Следите за **[стеком вызовов](/glossary/#stek-vyzovov)** — он показывает, какая процедура кого вызвала, и помогает понять, откуда пришло выполнение.

## Шаг 4. Отладка в Предприятии (без Конфигуратора)

Включите **«Отладка по требованию»** в настройках Предприятия. Тогда Конфигуратор может подключаться к запущенному сеансу и ставить точки останова без полного запуска под отладкой — удобно на работающей базе.

## Типовые грабли

- **Точка не срабатывает.** Проверьте, что сеанс запущен с отладкой, а не обычным запуском.
- **Переменная пустая.** Включите табло выражений и проверьте тип и значение; часто причина — неверный контекст (сервер/клиент).
- **Отладка на сервере.** Для серверного кода нужна возможность отлаживать на сервере; в файловом режиме это проще.
- **Цикл не кончается.** Поставьте точку и пройдите F10 — видно, на каком шаге условие не срабатывает.

- Быстрая проверка кода — [консоль кода](/glossary/#konsol-koda).
- Незнакомые термины — [Глоссарий](/glossary/).

**[Подписка на событие](/glossary/#podpiska-na-sobytie)** — способ выполнить свой код, когда в другом объекте что-то происходит (запись документа, проведение), не меняя сам объект. Удобно для доработок типовой: ваша логика живёт отдельно и не мешает обновлениям.

## Что такое подписка на событие

Подписка «привязывается» к **источнику события** (например, документ «Реализация товаров») и к конкретному событию (например, «Обработка проведения»). Когда событие наступает, платформа вызывает процедуру подписки.

Ключевой приём — параметр **[Отказ](/glossary/#otkaz)**: установка `Отказ = Истина` отменяет действие (запись, проведение).

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| Подписка на событие | объект, выполняющий код при событии другого объекта |
| Источник события | объект, на событие которого подписываемся |
| Отказ | параметр, отменяющий действие |

## Шаг 1. Создайте подписку

В Конфигураторе: **Общие → Подписки на события → Добавить**. Укажите:

1. **Источник** — объект или всё приложение.
2. **Событие** — например, `ОбработкаПроведения` или `ПередЗаписью`.
3. Имя процедуры в модуле подписки.

## Шаг 2. Напишите процедуру

```bsl
Процедура КонтрольОстатков(Источник, Отказ, РежимПроведения) Экспорт

    Запрос = Новый Запрос;
    Запрос.Текст =
    "ВЫБРАТЬ
    |    ТоварыНаСкладах.КоличествоОстаток КАК Остаток
    |ИЗ
    |    РегистрНакопления.ТоварыНаСкладах.Остатки КАК ТоварыНаСкладах
    |ГДЕ
    |    ТоварыНаСкладах.Товар = &Товар
    |    И ТоварыНаСкладах.Склад = &Склад";
    Запрос.УстановитьПараметр("Товар", Источник.Товар);
    Запрос.УстановитьПараметр("Склад", Источник.Склад);
    Результат = Запрос.Выполнить().Выбрать();

    Если Результат.Следующий() И Результат.Остаток < Источник.Количество Тогда
        Сообщить("Недостаточно товара на складе!");
        Отказ = Истина;
    КонецЕсли;

КонецПроцедуры
```

## Шаг 3. Проверьте

> **Проверка.** Попробуйте провести документ с количеством больше остатка — проведение должно отмениться с сообщением. Скорректируйте количество — проведение пройдёт.

## Типовые грабли

- **Процедура не вызывается.** Проверьте, что подписка привязана к правильному источнику и событию, а имя процедуры совпадает с указанным.
- **Не отменяется действие.** Параметр `Отказ` должен быть объявлен в сигнатуре процедуры и установлен в `Истина` до завершения.
- **Подписка мешает обновлениям.** Держите логику в подписке отдельно от объекта — это и есть её смысл.
- **Событие срабатывает слишком часто.** Уточните источник (конкретный документ) вместо «всё приложение», если нужен один объект.

- Пошаговый разбор логики — [«Отладка в 1С»](/cheats/debugging-1c/).
- Контроль остатков в проведении — [стандарты v8std](/glossary/) и справочник стандартов.
- Незнакомые термины — [Глоссарий](/glossary/).

«Конвертация данных 3.0» (КД 3.0) — инструмент 1С для настройки обмена на основе **[формата EnterpriseData](/glossary/#enterprisedata)**. Этот формат — стандарт обмена прикладных решений, и на нём строятся новые обмены между конфигурациями.

> **Требование стандарта.** «Новые обмены на основе правил конвертации не разрабатывайте» — [std771 «Интеграция прикладных решений через формат EnterpriseData»](https://v8std.ru/std/771/). Обмен между конфигурациями на БСП выполняется на основе формата EnterpriseData.

## Что такое КД 3.0 и EnterpriseData

- **[EnterpriseData](/glossary/#enterprisedata)** — формат обмена: набор пакетов XDTO, которые описывают данные (справочники, документы и т.п.) в едином виде. Его используют типовые конфигурации на БСП.
- **[КД 3.0](/glossary/#kd30)** — конвертация данных на базе этого формата: правила описывают, как данные одной конфигурации ложатся в структуры EnterpriseData и как из них получаются данные другой конфигурации.

Проще говоря: в [КД 2.0](/cheats/conversion-rules-1c/) правила были «сами по себе», а здесь правила работают поверх общего формата обмена.

## Словарик новичка

| Слово | Что значит |
| --- | --- |
| EnterpriseData | формат обмена прикладных решений (набор пакетов XDTO) |
| Пакет XDTO | объект метаданных, описывающий структуру данных формата |
| КД 3.0 | конвертация данных на основе EnterpriseData |
| Версия формата | номер вида Major.Minor (например, 1.4) |
| БСП | Библиотека стандартных подсистем |

## Версии формата EnterpriseData

- Актуальные версии формата берут из **последней опубликованной версии БСП**.
- Формат поставляется как объекты метаданных **`Пакет XDTO`** с именами вида `EnterpriseData_{X|XX}_{Y|YY}_{Z|ZZ}`, где X и Y — Major-версия, Z — Minor.
- Обмен должен поддерживать **все актуальные версии** формата. Пример: если встроенная БСП 2.4.1 поддерживает 1.2, 1.3 и 1.4 — обмен поддерживает все три.
- Нельзя выпускать версию конфигурации, которая не поддерживает какую-либо из версий формата, поддерживаемых встроенной БСП.
- Версию формата не поддерживают, если она не соответствует функциональным требованиям. Пример: обмен документами «Чек ККМ» есть только в версии 1.4 — значит поддерживаемые версии не ниже 1.4.
- Если совместно поддерживаемых версий нет (например, у конфигурации сильно устаревшая версия), обмен невозможен. В этом случае пользователям сообщают, какие версии поддерживаются.

> **Не для передачи данных.** Свойство `AdditionalInfo` формата не используют для передачи сведений между конфигурациями — только для поддержки законодательства или обхода критических ошибок. Состав свойств формата расширяют согласованно.

## Что понадобится

- Обе конфигурации на БСП.
- Инструмент «Конвертация данных 3.0» и документация по нему на ИТС.
- Согласованный набор версий формата EnterpriseData для обеих сторон.

## Как это устроено

1. **Определите версии формата.** Посмотрите, какие версии EnterpriseData есть в БСП обеих конфигураций, и выберите те, что поддержаны с обеих сторон.
2. **Опишите правила конвертации** поверх структур EnterpriseData: какие объекты и реквизиты одной базы соответствуют данным другой.
3. **Настройте обмен** штатными механизмами (планы обмена) или через инструмент конвертации.

> **Проверка.** После обмена проверьте, что объекты появились в приёмнике и ссылки на связанные объекты заполнены.

## Типовые грабли

- **Несовпадение версий формата.** Стороны поддерживают разные версии EnterpriseData — обмен не идёт. Сверьте набор версий в БСП обеих конфигураций.
- **Версия не поддержана обменом.** Обмен не реализует какую-то из версий, поддерживаемых встроенной БСП, — это нарушение требования стандарта.
- **`AdditionalInfo` для передачи данных.** Так делать нельзя: свойство — только для законодательства и критических случаев.
- **Расширение состава свойств «на своей стороне».** Состав свойств формата меняют согласованно, иначе обмен расходится.
- **Устаревшая конфигурация.** Совместно поддерживаемых версий может не быть вовсе.
